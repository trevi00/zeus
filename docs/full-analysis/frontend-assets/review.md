# 프론트엔드·스펙·디자인·검증·공통 템플릿 정적 검토

검토자는 Codex의 독립 검토 에이전트다. 실제 Claude 검토 결과가 아니며, 구현·채택 승인도 아니다. 상류의 지시문은 분석 대상 데이터로만 읽었다.

## 범위와 증거 수준

`harness@a3f8b3be9a0a389329de6e16a6c7db81782041a3`의 지정된 6개 파티션, **47개 경로 93,217바이트**를 전문으로 읽었다. 각 파일의 Git blob, 원본 크기, SHA-256을 고정 manifest와 대조한 결과는 `files.json`에 있다. 읽기 범위와 의미 검토 범위를 구분했다. 연결 구현·설정·테스트는 `supporting-evidence.json`의 해당 행 범위만 근거로 사용하며 47개 외 전체 파일 커버리지에 더하지 않는다.

**상류 코드 실행·테스트 실행·브라우저 조작·실기기 실행은 모두 0건**이다. 이 작업은 지정된 읽기 전용 정적 검토다. 문서가 인용한 별밤·code-tutor 등의 과거 실측은 상류의 주장으로 분류했다. 이 검토에서 해당 앱, 당시 실행 로그, 외부 React/arc42 원문을 재검증하지 않았다. 따라서 전체 하네스 분석 완료나 실제 동작 입증으로 확장할 수 없다.

## 주요 발견

### FE-01 — 모킹 지침을 사용자 요구로 오인해서는 안 된다

`react-vitest.md`는 컴포넌트/단위 범위라고 명시하면서 MSW, fakeTimers, 네트워크·시간·스토리지 모킹을 권한다. 이것을 실제 E2E라고 속이는 문서는 아니지만, 사용자의 모킹하지 않는 환경 구축 요구와는 차이가 있다. `userEvent` 역시 실제 기기 측정이 아닌 DOM 사용자 동작 시뮬레이션이다. Zeus에는 실제 서비스·격리 데이터·초기화 계약을 사용하는 흐름으로 바꿔야 한다. 컴포넌트 단위 검사의 별도 허용 여부를 임의로 사용자 합의에 추가하지 않는다.

### FE-02 — 템플릿이 약속하는 의미와 게이트가 재는 문자열이 다르다

`graph_queries._coverage()`는 원본의 정규식 ID 목록을 대상 전문의 부분 문자열 포함으로 대조한다. `_partition()`도 각 ID가 포함된 파일 수만 센다. 앵커 0건과 파일 0건을 거부하는 것은 실제 방어지만, AC의 행동·결과나 화면 가시성을 검증하지 않는다. `REQ-1`이 `REQ-10`에 포함되는 충돌, 주석/Non-Goal 언급으로 충족되는 문제를 상류 PRD 스킬도 자인한다.

더 직접적인 템플릿 모순은 다음과 같다.

- `domain-spec.template.md`는 `EP-010~019` 범위 표기를 허용한다. `_partition()`은 중간 ID를 확장하지 않으므로 실제 EP-011 등이 원본에 있다면 이 표기만으로는 배속되지 않는다.
- `component-diagram.template.md`의 prose `→`와 Mermaid `-->`는 의도적 분리이다. 후속 스킬 전문 검토로 기존의 화살표 충돌 해석을 정정했다. 현재 검사기는 문서 전체 정규식이며, 설명문·그래프·실제 코드 사이 의미 정합은 별도 검증이 필요하다. [정정 근거 DM-01](../diagram-mobile-assets/review.md#dm-01-다이어그램-소비-계약과-기존-보고-정정)을 참고한다.
- `conceptual-design.template.md`는 usecase의 모든 명사를 전사한다고 약속한다. 실제 카탈로그는 명사 추출을 포기하고 UC ID 백참조 존재로 환원했다고 명시한다.
- templates README는 SEQ/ST 질의가 pending이라고 적지만, 현재 카탈로그는 각각 UC 문자열 및 `_state` 접미 컬럼 문자열 커버리지를 구현했다. 파일이 있어도 상태 전이나 실패 경로 의미가 검증되는 것은 아니다.

Zeus의 구조화된 ID 참조와 active/retired 규칙은 부분 문자열 충돌을 피하는 방향이다. 다만 현재 `validate_spec(previous=...)`는 요구 statement/risk의 의미 변경을 새 ID로 강제하면서, 기존 시나리오의 Given/When/Then 변경에는 같은 제약을 두지 않는다. 사람 승인·실행 증거가 spec hash에 묶여 철회되어야 하며, 시나리오 ID의 의미 변경 정책도 명시적으로 정해야 한다.

### FE-03 — API 명세 템플릿이 최신 스킬·게이트를 따라가지 못한다

API 스킬은 EP별 요청/응답, 오류 코드·HTTP·EP·계층 표, 전송 헤더, 인증 축, 실패 우선순위, 소비 화면을 요구한다. 템플릿은 요청/응답 JSON 1쌍, 인증 한 줄, 오류 산문 한 줄뿐이다. 현재 core 게이트는 `| HTTP` 문자열도 요구하는데 템플릿에는 이 표가 없다. 템플릿만 채워서는 최신 게이트 문장을 만족하지 않는다.

`각 엔드포인트에 요청/응답 JSON 예시`라는 게이트는 실제로 파일 전체에서 한 번의 ` ```json ` 문자열 존재를 확인한다. 같은 구간의 새 오류 표 게이트 주석은 전수 판정을 못 한다는 한계를 정확히 적으면서도 기존 JSON 게이트에는 같은 과장이 남았다. `seams.parse_contract_fields()`도 문서 전체 JSON 블록에서 키 집합을 합쳐 정합을 판단하며, 블록 하나만 파싱되면 HIGH가 된다. EP별 요청·응답·상태·헤더·필드 타입·중첩 경로 의미를 보장하지 않는다.

초기에 의심한 EP 제목 backtick 문제는 확정하지 않았다. 확인한 카탈로그는 제목 파싱 없이 `EP-\d+`를 전문 검색하므로 **backtick 자체를 현재 확인된 버그라고 보고하지 않는다.** 별도 API 추출기의 제목 파서는 이 범위에서 확인하지 않았다.

### FE-04 — GWT 최소 검사와 실제 실패 시나리오는 다르다

`usecase_lint.lint()`는 UC 섹션 안 Given/When/Then 문자열과 `실패`라는 단어가 있는지만 본다. 각각 연결된 정상·실패 GWT를 파싱하지 않는다. 같은 UC 안 AC ID 반복은 허용되며, 중복 UC ID 자체도 여기서는 거부하지 않는다. `intent_doc_floor`는 한글이 포함된 `<...>`와 extracted origin 및 앵커 부재를 잡지만 영어 placeholder나 인용되지 않은 evidence를 같은 수준으로 검증하지 못한다. frontmatter 부재도 명시적으로 거부하지 않는다.

`core.yaml`의 usecase 게이트는 이 린트에 연결돼 있다. forward requirements/PRD 단계에는 reverse-onboarding과 같은 intent floor 배선이 없다. 따라서 템플릿 주석의 강한 문장과 실제 기계 검사의 범위를 분리해서 흡수해야 한다. 실행하지 않은 정적 분기 분석이며, 엣지 입력은 격리 실행으로 추후 입증해야 한다.

### FE-05 — 디자인 및 사람 승인 배선은 revision 인증과 별개다

상류 디자인 critique의 실렌더·여러 상태·접근성·불확실 시 불통과·자기 채점 금지는 유용하다. 그러나 `gate_runner._external_verdict()`가 소비하는 외부 판정은 현재 읽은 함수에서 stage와 verdict_mode의 최신 값으로 선택된다. cycle redo에서는 철회하지만 statement별 구분, 파일/스펙 해시, 인증된 사람 신원을 이 함수가 검증하지 않는다. 상위 writer의 인증 보장은 이 파티션에서 확인하지 않았으므로 전체 인증 우회를 확정하지 않는다. Zeus는 승인 provider와 증거 해시를 명시적으로 구현하고 검사해야 한다.

### FE-06 — 문서 생성과 실제 소비 경로의 이름이 다르다

`scaffold_cmd.issue()`는 항상 `<type>.md`를 project 루트에 생성한다. domain-spec 템플릿/파이프라인은 `domain/<도메인>.md`를 소비하고 ontology-topology 단계는 `ontology/**`를 산출·검증한다. 이를 파일 생성으로 연결하는 별도 단계를 확인하지 못했다. `issue()`가 제공하는 기존 파일 거부도 `exists()` 후 일반 write이므로 원자적 독점 생성이 아니다. 동시 실행의 덮어쓰기 가능성은 정적 위험으로 남기며 재현했다고 주장하지 않는다.

`test_scaffold_smoke.py`는 24개 실물 수, frontmatter 시작, 게이트/계약 단어, PRD 발급과 재발급 거부, 일부 intent floor/추출기 동작을 확인한다. 모든 템플릿을 실제 각 단계에 넣어 게이트와 연결하는 검사는 아니다. 스택 특화 항목도 테스트 주석대로 실트리 스택 부재의 공통 fallback 확인이다.

### FE-07 — 스킬의 존재·이름 선언·실제 전달은 세 가지다

5개 React 파일은 모두 `name: frontend-react`, 6개 검증 파일은 모두 `name: verification`이다. router는 각 파일의 kind/frontmatter를 읽고 스택, 명시 이름, trigger 점수, 문자 예산으로 선택한다. 같은 이름의 최고점 1개 파일 우선 예약과 무득점 형제 강등이 있어 이름 하나를 선언한다고 관련 5/6개가 모두 전달되지 않는다. `omitted`와 `stack_filtered`를 공개하는 점은 흡수할 가치가 있다.

`step_cmd dispatch`는 실제로 `route()` 결과를 출력하지만 예외가 나도 fail-open으로 dispatch를 완료한다. core frontend-impl은 API 클라이언트 일치를 요구하며, 게이트의 단어가 스킬 선정에도 쓰인다고 주석에 명시한다. 즉 문장을 고치는 것만으로 전달 지침도 바뀔 수 있다. Zeus에서는 필수 계약·금전 흐름·검증 규칙은 예산 축소로 사라질 수 없는 계층으로 정하고, 선택적인 경험 지침과 분리해야 한다. 현재 router의 문자 예산은 Astra→Sol→Terra의 과업 동등성·회귀 검증을 통한 자격 부여가 아니다.

### FE-08 — 실제 경험 규율은 값이 있지만 사례와 일반 규칙을 분리해야 한다

흡수할 핵심은 실렌더부터 진단, 빌드 산출물 대상 테스트, 로그인 1회와 storageState, 멱등 시드, 공유 포트·계정·리미터 예산, 오류 본문뿐 아니라 헤더 확인, 저장 컬럼 정의역, 실제 DB, 시간 상한이 있는 대기, 과거 green/red의 트리·실행 ID 확인, 근본 원인과 인접 회귀 재실행이다. 다만 특정 burst=3, 90% coverage, 2회 반복, 화면 폭·모션·타이포 숫자는 프로젝트의 근거가 붙은 선택값이어야 한다. 숫자를 그대로 복사해 재현성을 얻었다고 주장할 수 없다.

tradeoff 스킬의 `scripts/cli/tradeoff_lint_cmd.py` 자체 점검 명령은 고정 tree에 없다. 실제 배선은 `scripts/validators/tradeoff_lint.py`다. validator는 등록된 지표·연산자·대안을 검사하고 의미 타당성을 약속하지 않는 점을 분명히 한다. 이전 CLI에서 validator로 이동했다는 소스 설명과 스킬의 오래된 명령이 어긋난다.

## 채택 제안과 후속 검증

이번 판단은 모두 **adapt 제안, 미승인·미흡수**다. 코드의 문자열 게이트를 그대로 이식하는 대신 구조화된 스펙과 실행 오라클, 환경 영수증, 독립 승인, 티켓 원장을 연결해야 한다. 내부 코드는 stdlib domain/application과 IO adapter로 분리하고 Git은 정의, PostgreSQL은 실행 상태의 정본으로 유지한다. 상류 Markdown frontmatter의 trust/author는 증거 데이터일 뿐 권한으로 승격하지 않는다.

필요한 후속 검증은 (1) 47개 원본에 대한 실제 Claude 독립 검토 및 비교, (2) 격리된 scaffold/router/graph/usecase/tradeoff 기존 테스트와 위 모순의 최소 재현, (3) 실제 frontend/API 프로젝트의 양방향 계약·실행 환경·초기화·반복 테스트, (4) 인증된 사람 QA와 스펙 변경 시 승인 철회, (5) 알파/점진 배포/복구/CS 전체 연결이다. 삼성 실기기와 Device Farm SDK/MCP/live/replay는 이후 기기 단계에서 실제 구현·측정해야 하며 이 문서가 그 완료를 대신하지 않는다.

외부 React·arc42·접근성 숫자의 현재 적합성과 라이선스/출처는 원문 자료로 재확인해야 한다. 이 정적 검토는 외부 기술 권고를 검증한 연구가 아니다. 인용된 경험 로그 원본 및 해당 프로젝트 실행 상태의 추가 분석도 남아 있다.
