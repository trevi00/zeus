# 설계 결정 D-004–D-031 전문 검토

고정 원문은 `harness-design` 커밋 `20147dde412c1f2d84178d5c3665157ced1e7334`의 `design/decisions`다. `harness-design:design/decisions:001` 32개 중 앞선 파티션의 D-001–D-003을 제외한 **29개 문서 전문**을 읽었다. D-006의 본 결정과 후속 정련은 별개 파일이다. 본문 읽기는 완료했지만, 각 문서가 인용한 큰 초안·외부 리서치·현재 구현·테스트의 전수 추적은 남았다. 아래의 과거 승인·실측·성공 주장은 이번 실행 증거가 아니다.

| 원문 | 검토 결과와 Zeus 적용 판단 |
|---|---|
| D-004 ontology | 5평면, provenance/trust 분리, 타입·관점·엣지·생산자/소비자 계약은 적응 후보다. 경로 기반 ID는 rename/retraction과 일체로 다뤄야 한다. 설계 정본이 추후 스키마 파일로 넘어간다는 조건을 실제 파일 존재·등록으로 확인해야 한다. 7→8축과 후속 kind 추가가 있으므로 최초 enum 개수로 구현을 고정하지 않는다. |
| D-005 pipeline | 상태를 파일 존재 대신 검증 이벤트에서 도출하고 DAG와 표시 순번을 분리하는 원칙을 보존한다. 29개 산문을 8개 실행 check로 전부 사상했다는 주장은 현재 검사기의 의미 검증이 필요하다. 원문 자체에 e2e feedback retarget 유도 불능과 view 소비자 부재가 남아 있다. 사용자 8단계 SDD와 원문 15/16단계 설계를 별도 계층으로 매핑해야 한다. |

| D-006 refinement | 첫 심각 실패/같은 실패 2회에서 조사, 이후 토론으로 비용을 단계화한다. 문서는 처음에 적용 예정·체크박스 미완료였고 D-007이 후속 확정한다. 반복의 지문·독립 발생 ID·수리 후 재판정을 명시해야 하며, “다음에는 조사 없이 수리”에는 코드·환경·증거의 신선도 조건이 필요하다. |
| D-007 execution | 실패 종류와 총 재시도 예산을 분리하고, 진전과 재시도도 구분한다. CC Stop 훅·단일 스포너·cron은 플랫폼 구현 선택이다. Zeus의 호스트 supervisor/실행기와 계약으로 대응해야 한다. depth와 절단 간선 수만으로 분해 품질을 보장한다는 표현은 범위를 좁혀야 한다. 원본 OS lock 유실 실측은 이번 Windows 검증이 아니다. |
| D-008 convention | 공통·스택·프로젝트 오버레이와 도메인별 규칙, 조사한 대상 수를 함께 제시하는 방식은 적응 후보다. premises 면제와 produced 검증을 구분한다. design-token을 별도 디자인 하네스에 위임했으므로 원본 전체 설계 완료가 디자인 구현 완료를 뜻하지 않는다. |
| D-009 residual | 사람 검토 대기 노드만 멈추고 독립 노드를 계속하는 방식은 필요하다. “machine/render 가능하면 human 선언 금지”는 사용자의 실제 UI·인수 검토 요구에 그대로 적용할 수 없다. actor=operator 문자열은 실제 사람 판정의 인증이 아니다. 문서의 critic 스텁을 작성자 자체 검증으로 보완한 사실도 독립 검토와 분리한다. |
| D-010 routing | 후보 검색·매칭·예산 주입을 분리하고 단위를 표시하는 원칙을 보존한다. 상시 PPR, 임베딩, 공격적 기본값은 현재 비용·정확도 실측 없이 채택하지 않는다. 파라미터 튜닝과 승인 조건 튜닝을 분리하고, Sol/Terra 자격은 평가 지표뿐 아니라 동일 행동·회귀 조건으로 확인한다. |
| D-011 sandbox | 후보 변경과 검증기의 권한·수명을 분리하는 원칙을 검토한다. Docker/환경 충실도와 held-out 판정기 비노출이 실제로 성립하는지는 별도 증거가 필요하다. 같은 파일 경로를 “불가침”이라 부르는 것만으로 경계가 생기지 않는다. 이후 D-030이 Docker 전제를 worktree 정확성 격리로 바꿨으므로 최초 결정만 인용하지 않는다. |
| D-012 improvement | 감지→갱신→기록→평가, 발생 출처, 회귀 검증, 자동 청소의 폐회로는 핵심 흡수 후보다. 5턴·14/45일·0.95·30세대와 비용 절감 수치는 원본 관측/시드다. 여러 번 harvest한 동일 근거를 독립 실패나 학습 성과로 세면 안 된다. archive와 retraction, 원본 승인과 새 환경 승인도 분리한다. |
| D-013 closeout | 소비자 동반 등록·깊이 상한·파라미터 조정 방향은 계약으로 추적한다. “잔여 0” 뒤에도 curator·calibration·MCP 실제 배선이 구현 조건으로 남는다. coding/chat 필터 한 개라는 비용 설명은 저장·권한·삭제·검색 교차 영향의 검증이 아니다. |
| D-014 reverse | 코드 구조의 추출, 사람의 의도, 추정 행동을 분리하는 설계가 사용자 SDD 요구에 부합한다. 숫자 confidence·인용 span 존재가 의미적 참을 인증하지 않는다. 사용자 WHY/KPI/Non-Goals를 자동 발명하지 않고 사람이 검토할 수 있는 제안으로 내야 한다. 15단계 표기는 D-008의 16단계 개정과 대조가 필요하다. |
| D-015 recovery | liveness와 자산 복원, 별도 감시와 bake 관찰, 불확실 결과를 분리한다. 2026-09-07 후기는 OS 권한 밖 감시가 실제로 성립하지 않았음을 자인한다. 이 후기와 Guardian의 실제 검토를 함께 보존한다. 같은 계정의 디렉터리 분리는 독립 권한 경계의 증거가 아니다. |
| D-016 spiral | 위험 우선순위는 DAG 제약 안에서 적용하고 prototype은 인수 PASS와 분리한다. cycle plan의 다음 소비자가 필요하다. “연속 컨텍스트 완전 지원”은 문서의 판정이며 D-050의 두 도출기 불일치·재개방 문제와 함께 재평가해야 한다. |
| D-017 scale | solo/fleet 논리 계약과 물리 backend 분리는 후보지만, Kafka→Git JSONL 정본/PG projection/Redis 비버스는 Zeus의 Git 정의·PG 런타임 SSOT와 직접 다르다. 기능 목적을 흡수하되 이 저장 계층 권위를 그대로 이식하지 않는다. 무료 subscribe·벡터 수 임계·2026 표준 스택·비용 절감은 재검증 전 주장이다. |
| D-018 details | 채팅의 응답 후 정착, 용어 사전, 인터뷰, 재개, REPL 수명과 키 분리는 검토 대상이다. instruction 지식을 전역 명령 권위로 승계하지 않는다. 여기서 확정한 resume·비동기 consolidate는 D-030에서 바뀐다. 참조된 glossary 실물과 하네스 안 stub의 차이는 기존 design-canon 기록에 있다. |
| D-019 remining | 파일 전수 분석과 개념 흡수를 분리한 자기 정정 자체가 중요하다. compaction 등가 검사·감사 보존·테스트 오염 격리·tombstone·부재 정보 재라우팅은 흡수 후보다. 공통 envelope는 Zeus 육하원칙 버전 메시지로 대응해야 한다. mutation score는 변이 범위와 살아남은 사례의 의미를 함께 확인한다. |
| D-020 remining | lease 양측 fencing, 실제 진전, 실패 가능한 복구 쌍, 개선 전후 비교 증거는 후보다. clock·갱신 지연·중단된 owner의 외부 부작용까지 봐야 fencing을 입증할 수 있다. “PASS 동결”은 입력·정책·코드 변경 때 무효화해야 한다. 문서가 남긴 미정독 자산도 전체 분석 분모에서 빠뜨리지 않는다. |
| D-021 surfaces | CLI·커맨드·계층·상태 경로의 카탈로그는 사용자 표면과 구현 표면을 연결한다. 표면 개수가 적다는 것은 자동화 성과의 단독 증거가 아니다. AST import 규칙은 동적 호출·실제 IO·권한을 전부 검증하지 못하므로 목적별 경계를 유지한다. |
| D-022 skeleton | 하네스/감시자/프로젝트와 각 원장의 스코프 구분은 필요하다. 트리 밖 guardian·원자 swap·ignore=projection은 현재 구현 검증 없이 완료로 세지 않는다. 프로젝트 런타임 역시 Zeus PG에서 프로젝트 식별자와 버전으로 구분해야 한다. |
| D-023 sessions | 실행 전 멱등키를 쓰고 키 존재만으로 이후 실행을 건너뛰면, 키 저장 뒤 외부 동작 전 중단의 결과를 판정할 상태가 부족하다. pending/실제 결과/불확실/재확인 경로까지 추적해야 한다. durable execution 제품과 닮았다는 문구는 효과 보장의 증거가 아니다. 사전 계산 결과는 오래된 입력과 권한으로 자동 실행되지 않아야 한다. |
| D-024 hooks | 이벤트별 결정론 디스패처·정책 데이터 분리·관측 스팬은 후보다. 휴리스틱 유입 스캔은 위험 신호이며 신뢰 보증이 아니다. 프롬프트를 attribute 대신 event에 넣는 것만으로 민감 데이터 문제가 해결되지 않으므로 필요한 관측 필드·보존·노출을 따로 설계한다. |
| D-025 cards | 기계가 읽는 capability 카드와 AGENTS 렌더링을 실제 도구 권한·검수 자격과 구분한다. tamper-evident 기록은 누가 어떤 권한으로 내용을 작성했는지까지 자동 인증하지 않는다. 다른 제품의 instruction 우선순위도 단순 렌더링으로 호환됐다고 할 수 없다. |
| D-026 snapshots | rollback/known-good/compaction/frozen/baseline/export를 구분하고 원장은 앞으로만 진행시키는 계약은 중요하다. Git 태그의 트리 원자성과 여러 파일의 live 교체 원자성은 별개다. DB migration·실행 중인 작업·증거 보존까지 복구 범위를 명시해야 한다. |
| D-027 state | 저장 상태·파생 뷰·메타·캐시·in-flight·복구를 분리하고, 과거 의미 보존을 검사한다. unknown 필드 수용이 unknown 이벤트의 승인이나 필수 의미 누락 허용으로 번지면 안 된다. 과거 로그 재생 동등성은 새 이벤트의 생산·소비 검증과 함께 필요하다. |
| D-028 templates | 템플릿·스키마·실행 게이트를 같은 artifact type에 연결하는 계약이 현재 템플릿 분석과 직접 연결된다. 모양이 있는 것과 의미 검사가 가능한 것을 구분한다. 팀·일별 예산은 동시 예약/정산/중단을 포함해야 한다. 차등 증거 배포는 검수 독립성의 보조 수단이며 필수 사실을 누락시키는 근거가 아니다. |
| D-029 design | Git 토큰·외부 디자인 표현·컴포넌트 매핑을 나누는 방향은 후보다. Figma/MCP/표준 버전·성능 숫자는 공식 원문과 현재 API 검증 전 주장이다. 사람 라벨과 심판 보정을 유지하고, 모델 이름 분리만으로 독립성을 인증하지 않는다. |
| D-030 alignment | 이전 결정의 resume→fresh-spawn, 직접 human verdict→check 후 단일 합산, 비동기→가벼운 동기 정착, Docker→worktree 정정을 명시한다. 외부 Codex 미인증을 웹 연구로 대체한 기록은 실제 Codex 검수가 아니다. atomic rename만으로 동시 read-modify-write의 유실이 방지되지는 않는다. fallback 상태 노출·튜닝 중단은 적응 후보다. |
| D-031 retrospective | 정상 긴 턴·세션 교대·idle/done을 장애와 구분하고, 복원과 계속 실행을 분리하는 운영 경험이 중요하다. stage_started와 모든 dispatch를 같은 시도 수로 세지 않는다. Java 전용 산문 게이트와 구현 없이 E2E READY였던 과거 실패는 실제 사용자 시나리오 검증의 필요성을 보여준다. mutation 1.0·회귀 완료는 당시 범위의 주장으로 남긴다. |

## 다음 검증과 채택 경계

1. 앞선 결정과 D-030/D-050 등 후속 개정을 연쇄로 읽어 최종 계약을 구성한다. 선언의 “확정/완결”을 현재 동작으로 옮기지 않는다.
2. 파이프라인 담당자의 config/ontology/pipeline/agent 추적, 프론트 담당자의 template/parser/gate 추적, 기존 Guardian 및 lib 영수증과 연결한다. 정적 반례를 실제 실행 성공/실패라고 부르지 않는다.
3. Zeus는 Git 정의·PostgreSQL 런타임 SSOT, 버전별 티켓·증거, 독립 검수, 실제 사용자 인수라는 현재 계약을 유지한다. 과거 사용자 승인과 capability 문자열은 새 실행 권한이 아니다.
4. 이 29개는 `body_reviewed_call_test_trace_pending`으로 기록한다. 원문 해시를 확인하되 인벤토리·해시 일치를 의미 검토나 실행 검증의 대체물로 쓰지 않는다. 실제 upstream 테스트 실행은 이 파티션에서 0건이다.
