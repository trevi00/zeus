## 1. The omitted cross-example condition — confirmed, and it is worse than a branch bug

Root is right that I missed this, and it is the most consequential technical finding in the set.

Re-reading `paygate-kovan.md:142-156` against `flutter-native.md:131-150`: the native example computes `isSuccess = resultCode == Activity.RESULT_OK && ansCode == "0000"` (`:146`), then serializes `responseCode = if (isSuccess) "0000" else ansCode` (`:150`). When `resultCode` indicates failure but `ansCode == "0000"`, `isSuccess` is false yet `responseCode` is set to the raw `"0000"`. The Dart model derives `bool get isSuccess => responseCode == '0000'` (`flutter-native.md:142`) and therefore reads that failure as success.

Sharper than the branch itself: **the boundary discards the `resultCode` dimension entirely.** `isSuccess` is computed natively and then never crosses the channel — only `responseCode` does. So the two-factor rule that `paygate-kovan.md:224-225` states as mandatory ("`Activity.RESULT_OK`만으로 부족… VAN 응답 코드까지 확인") is unreconstructable on the Dart side by design of the documented serialization. This is a contract/serialization gap, which is a different and more general defect class than a mis-set flag.

Two further strands, both undetermined from documentation alone:

- `flutter-native.md:34` states the response map is "29개 필드 + isSuccess 포함" — i.e. `isSuccess` *is* transmitted — while `:142` derives it locally from `responseCode`. The two documents disagree on whether the flag crosses the channel. If it is transmitted and consumed, the condition may not materialize; if derived, it does. Which holds in the unseen app is unknown.
- `paygate-kovan.md:238` states KOVAN's success `resultCode` is **1**, not `Activity.RESULT_OK`. By the same file's later section, the earlier template's `resultCode == Activity.RESULT_OK` comparison is wrong for the VAN the file is named after, so on genuine KOVAN success `isSuccess` would be false and `responseCode` would carry the raw vendor code. The resulting error direction depends on vendor code values I have not verified.

This is a static condition between two documented snippets. It is **not** an observed transaction, not a reproduced financial incident, and not evidence about the unseen application's behavior. As an SDD candidate it belongs in stage 1 and stage 6: money-flow states (approved / declined / cancelled / unsettled / unknown) defined by a human, with the native result code and the VAN code both carried across the boundary and asserted independently, verified against real approval status rather than a single field.
