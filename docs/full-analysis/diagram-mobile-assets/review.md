# 다이어그램·모바일·온톨로지·역설계 자산 정적 검토

고정 원본 `harness@a3f8b3be9a0a389329de6e16a6c7db81782041a3`의 지정된 9개 파일, 30,400바이트를 전문 검토했다. 원본 명령과 지시는 분석 데이터로만 읽었다. 원본 설치·실행·수정, 테스트 실행, 기기 조작은 하지 않았다. 파일별 의미와 SHA-256/Git blob 검증은 `files.json`, 직접 소비자·템플릿·테스트의 읽은 구간은 `supporting-evidence.json`에 기록한다. 후자는 이 파티션의 전문 커버리지에 더하지 않는다. 이 문서는 흡수 승인이나 실제 Claude 독립 검수 완료를 뜻하지 않는다.

## DM-01: 다이어그램 소비 계약과 기존 보고 정정

`component-diagram.md`는 모듈 의존과 데이터 소유 경계를 분리한다. 원문이 인용한 읽기 61건/쓰기 0건 같은 실측은 다른 프로젝트의 과거 주장으로 보존하며 Zeus의 실측으로 옮기지 않는다. 제외 항목과 사유를 명시하게 하는 접근은 Zeus 경계 설계의 후보 자산이다.

**기존 frontend-assets 보고의 화살표 불일치 해석을 정정한다.** 스킬과 `component-diagram.template.md`는 설명문에 `→`, Mermaid 그래프에 `-->`를 쓰도록 의도적으로 분리했다. 따라서 설명문 기호와 카탈로그 기호가 다르다는 이유만으로 템플릿 결함이라고 할 수 없다. 현재 `_acyclic`은 Mermaid AST가 아니라 문서 전체에 정규식을 적용한다. 설명문에서 Mermaid 기호를 피하는 이유는 이 중복 소비를 피하려는 것이다. 남는 검증 공백은 그래프 문법·렌더링, 설명문과 그래프의 의미 정합, 실제 코드 의존과의 일치이다. 읽은 단위 테스트는 간단한 간선 문자열의 순환/비순환 예제를 검사한다. 실제 Mermaid 렌더 테스트는 읽은 테스트 파일에 나타나지 않았다.

`diagram-anchor.md`의 소비자 우선, 앵커 실제 일치, 0건 결과 경계는 가치 있는 교훈이다. 다만 원문의 역사적 공허 PASS를 현행 결함으로 취급하면 안 된다. 현재 `_ids`는 앵커 0건, `_acyclic`은 간선 0건을 FAIL로 반환하고, `test_graph_smoke.py`에는 앵커 부재 실패 사례가 있다. 테스트는 이번에 실행하지 않았다.

## DM-02: 시나리오를 문자열 커버리지로 대체할 수 없음

`flowchart.md`는 구체적 분기 조건과 실패 경로를 요구하고 FLOW 앵커를 후속 화면·테스트의 연결점으로 삼는다. 현재 카탈로그는 UC→flowchart, 모든 FLOW→wireframe을 검사한다. 원문의 사용자에게 보이는 흐름만 다루는 설명과 실제 모든 FLOW 검색 사이의 범위 계약을 정해야 한다. 원문의 UC 역참조 부재 공허 PASS 설명은 현행 `_ids`의 0건 거부로 이미 달라졌다. `_coverage`는 대상 텍스트에 ID 문자열이 있는지 검사하므로, 사람의 핵심 의도와 시나리오 의미를 보증하지 않는다.

`screen-flow.md`는 출발·도착 화면, 실제 조작 컨트롤, 선 종류를 대응시키고 모달·토글 등을 화면 전환과 구분한다. 다이어그램·설명·실제 UI의 양방향 대응은 SDD의 설계→구현→증적 연결 후보이다. 과거 61개 affordance 분석 수치는 재측정 전에는 Zeus의 품질 지표가 아니다. 읽은 파이프라인은 wireframe/ui-flow 산출물, FLOW 커버리지, 인간 렌더 검토를 연결하지만 실기기 전환 증적을 자동 수집하는 계약은 이 범위에서 확인되지 않았다.

`sequence-diagram.md`는 EP/UC 출처, 참여자·실행 순서·실패 우선순위를 다루고 API 계약 중복을 피한다. 카탈로그의 UC 존재 검사는 보상 처리·중복 결제·재시도 순서를 증명하지 못한다. `state-diagram.md`는 상태와 사건 로그를 나누고 trigger/guard/side effect/terminal 상태를 요구한다. 그러나 boolean은 상태가 아니라는 표현은 원문 사례의 판단이며 일반 규칙으로 채택할 수 없다. 실제 게이트는 논리 설계의 `*_state` 문자열을 찾고, 템플릿은 ENT와 ST 표 및 transition을 제공하나 guard/side effect를 독립 필드로 강제하지 않는다. 상태명·불법 전이·권한·사람의 의도를 구조화한 계약은 별도 설계해야 한다.

## DM-03: 온톨로지의 현행 방어와 의미 검증 공백

`ontology-anchor.md`는 생산자·소비자의 앵커 합치, 분할 전사, 읽기/쓰기/제외, 최소 두 관점의 분류를 강조한다. 원문의 CON 불일치와 미선언 스킬 수치는 역사적 상태이다. 현재 카탈로그는 `CON-`을 사용한다. 또한 현재 `ontology_validator.py`는 JSON Schema, confidence 값, extracted evidence, ID 중복 및 dangling edge를 검사한다. 그러므로 이 방어가 없다고 보고하면 안 된다. 읽은 계약 테스트에도 중복 ID와 dangling edge 실패 사례가 있다.

현재 구조 게이트의 한계는 남는다. `_load_jsonl`과 검증 루프는 비어 있는 nodes/edges 목록에 최소 개수를 요구하지 않는다. 파이프라인의 facets 2축 게이트는 YAML 의미·축 개수 대신 `axis-2` 문자열 존재를 검사한다. 따라서 두 JSONL이 비어 있고 facets에 해당 문자열만 있는 경우 구조 게이트가 통과할 수 있다는 **정적 추론**이다. 재현 실행은 하지 않았으며 이후 인간 승인까지 통과한다고 주장하지 않는다. `ontology-topology.template.md`의 Markdown 축 도표를 실제 JSONL/facets 파일로 변환하고 의미를 대조하는 연결도 읽은 구간에서 입증되지 않았다.

## DM-04: 역설계는 인간의 요구와 실행 증적을 대신하지 않음

`reverse-extraction.md`는 extracted 산출물을 손으로 수정하지 않고 재추출·검증하도록 한다. 현재 runner에는 다음 경계가 보인다. 모두 코드 정적 판독이며 재현 실행 전이다.

- 기존 파일 보호는 origin이 `None` 또는 `extracted`이면 덮어쓰도록 되어 있다. origin 없는 사람이 작성한 문서의 보호는 이 조건으로 보장되지 않는다. 읽은 테스트는 명시적 authored origin을 보호하는 사례만 확인한다.
- `source_commit`은 HEAD 앞 12자리이며 추출은 작업 트리를 읽는다. 읽은 생성 경로에는 dirty tree 또는 실제 입력 파일 해시 결합이 없다. 동일 HEAD라는 이유만으로 입력 바이트 재현성이 성립하지 않는다.
- `--verify`는 디코딩된 텍스트를 비교한다. 원문이 말하는 바이트 동일성과 달리 개행 정규화 차이를 놓칠 수 있다. 어떤 추출기도 산출물을 반환하지 않으면 drift가 없다고 판단하며, 소스가 전혀 없는 경우 main의 언어 비율 방어도 적용되지 않는다.
- 알 수 없는 `--only`는 빈 보고서를 만들 수 있고 main은 성공 코드를 반환한다. verify에는 `--only` 선택이 전달되지 않는다. 의도한 부분 추출의 성공과 명령의 정상 종료를 구별해야 한다.
- 등록된 추출기는 Python 및 TypeScript 계열이며 읽은 registry에는 Dart 추출기가 없다. Flutter 문서가 존재한다고 모바일 코드 역추출이 구현된 것은 아니다.

Zeus에는 입력 해시·원본 커밋·dirty 상태·추출기 버전·산출물 바이트 해시·선택한 범위·관측 건수의 영수증, authored 소유권, 빈 결과 의미를 먼저 설계할 후보로 옮긴다. 이 문서에서 구현하지 않았다. 기존 reverse smoke 테스트는 합성 소스 파일로 추출·수정 drift를 확인하는 검사이며 실제 서비스를 끝까지 실행한 인수 증거가 아니다.

## DM-05: Flutter 경험의 범위와 Samsung 기기 단계

`flutter-layering.md`는 실제 원본 3개 앱의 controller/service/dao, Result·예외 변환, screen/screenmodel, Riverpod, route/API registry 관례를 수집한다. POS와 KDS/TO의 ChangeNotifier/Notifier, Riverpod 버전, singleton/provider DI 차이를 스킬이 명시한다. 이 차이를 하나의 전역 규칙으로 합치면 안 된다. 원문 자체가 테스트 확인 부재를 명시하므로 계층 관례를 검증된 테스트 자산이라고 부르지 않는다. 현재 제품·라이브러리의 최신 권고로 추천하지 않으며 향후 채택 시 공식 자료와 실제 프로젝트 증거가 필요하다.

읽은 core mobile 단계는 선택적이고 backend gate 이후이며 Flutter build/analyze, API registry 대조를 제시한다. router 테스트의 pubspec/Gradle 합성 파일 판별은 Flutter 빌드·Samsung 실기기 테스트가 아니다. 이 스킬에 Device Farm SDK/MCP/live/replay 실행 구현은 없다.

Zeus `adapters/sdd.py`에는 ADB 정보 탐색과 Appium 코드 초안 생성 경로가 이미 존재한다. 탐색 결과는 `discovery_only`, `acceptance=false`로 구분하고, 생성 코드는 실제로 실행된 인수 증거가 아니라고 명시한다. 읽은 생성 경로는 금전 요구를 거부하고 활성 시나리오 한 개와 reset/환경 정보를 요구한다. 이것을 Device Farm SDK 구축 완료나 실제 기기 검증 완료로 승격하지 않는다. 실제 삼성 폰·태블릿 동작, SDK 선정, replay 반복 재현, 로그→시나리오 변환, 증적의 신뢰 체인은 사용자 결정에 따라 추후 단계이며 이번에 수행하지 않았다.

## Zeus의 8단계 SDD에 연결할 후보

| 단계 | 이번 자산의 연결 후보 | 통과에 추가로 필요한 증거 |
| --- | --- | --- |
| 1 스펙 논의 | UC/FLOW 출처, 역추출과 사람이 의도한 요구 구분 | 사람이 확인한 핵심·실패·금전 시나리오 |
| 2 디자인 분석 | screen-flow, sequence, state, component, 다축 온톨로지 | 실제 화면 렌더와 전이·guard·API 의미 대조 |
| 3 코드 작성 | Flutter 앱별 계층, 경계와 registry | 선택 프로젝트·버전·플랫폼별 코드 연결 |
| 4 자체 검증 | 앵커/순환/구조 검사 및 추출 drift | Windows·WSL·Linux 환경 계약과 실제 통합 재현 |
| 5 알파 배포 | 문서·빌드 식별자를 추적할 증적 | 배포 실행·환경·빌드 해시·reset 관측 |
| 6 QA 및 증적 | 실제 조작과 FLOW/AC/EP/상태의 연결 | no-mocking 실기기 실행과 사람의 검토·승인 |
| 7 라이브 배포 | 시퀀스의 실패·보상 경계 | 점진 배포·중단·복구 관측 및 승인 |
| 8 CS 대응 | 사건 로그와 현재 상태 분리 | 개인정보 처리된 실제 로그→시나리오→재현 회귀 |

문자열 커버리지, 형식 검사, 코드 생성만으로 어떤 단계도 승인하지 않는다. Astra 설계·최종 검증, Sol 중요 구현, Terra 단순 구현의 자격 승급 역시 이 9개 문서에 입증된 실행 자산은 없다. 실제 동등 결과를 보여 주는 가드레일·비용·품질 관측이 먼저 필요하다.

## 남은 검토

9개 전문의 정적 분석은 완료했다. 실제 Claude 교차 검수, 원본 기술 주장에 대한 현재 공식 자료 검증, 라이선스/재배포 검토, 격리된 기존 테스트와 경계 재현, Zeus 적응 설계·구현·인수는 미완료이다. 연결 파일은 기록된 구간만 읽었으므로 해당 하위 시스템 전체 감사를 주장하지 않는다.
