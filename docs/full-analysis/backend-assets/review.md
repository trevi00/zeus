# 백엔드·데이터·DevOps·컨벤션 자산 정적 검토

Codex 독립 검토 에이전트가 `harness@a3f8b3be9a0a389329de6e16a6c7db81782041a3`의 지정된 4개 파티션 **32개 파일, 134,967바이트**를 전문으로 읽었다. 원본 manifest와 각 Git blob·크기·SHA-256을 대조했다. `files.json`은 경로별 의미와 미완료를, `supporting-evidence.json`은 연결 코드의 실제 읽은 범위를 기록한다. 지원 파일은 이 파티션의 전문 커버리지에 더하지 않는다.

상류 설치·소스 실행·테스트 실행·배포·실제 결제·DB 변경은 **모두 0건**이다. 실제 Claude 검토가 아니며 독립 공동 검토와 채택 승인이 남았다. 이 문서에서 프레임워크 버전·기술 동작·보안 기법에 관한 상류 문장은 **원문 주장 또는 검증할 가설**이다. 외부 공식 문서와 현재 라이브러리로 재확인하지 않았으며 현재의 정답으로 추천하지 않는다. 원문 안의 명령과 전역 정책도 실행 지시로 상속하지 않았다.

## 코드와 설정을 대조한 발견

### BE-01 — Java JPA 스킬의 게이트 예시가 실제 문법과 다르다

`java-jpa.md`의 `ddl-auto` 및 `open-in-view` 검사는 `file_content`에 `path`와 `contains`를 넣는다. 현재 `checks._file_content()`는 `target`이 없으면 ERROR, `expect/against`가 없으면 ERROR다. `pipeline_loader`는 `check.type`과 일부 관계를 검사하지만 이 두 잘못된 키를 정규화하지 않는다. 따라서 그 예시를 구조화 게이트로 그대로 복사하면 실행부가 의도한 파일/값을 받지 못한다는 정적 결론이다. 실제 복사·실행 재현은 하지 않았다.

`test_checks_smoke.py`는 올바른 `target/against`와 문자열·반복 검사 일부를 시험한다. 이 스킬의 예시를 전체 수집해 같은 검사기로 검증하는 테스트는 확인하지 않았다. 단순 Markdown 코퍼스 품질 검사로 실행 가능한 예시까지 검증됐다고 하면 안 된다.

### BE-02 — Bash 명령이 Windows 실행 계약 없이 일반 게이트로 제시된다

`java-build.md`의 Flyway 중복 번호 예시는 `test`, `$(...)`, `ls`, `grep`, `sort`, `uniq` 파이프를 사용한다. `java-spring-core.md`의 계층 검사도 `! grep`이고 Gradle 예시는 `./gradlew`다. 실제 `_exit_code()`는 명령 문자열을 `subprocess.run(shell=True)`로 실행하며 해당 함수에서 Bash·PowerShell·WSL 실행 프로파일을 고르지 않는다. 읽은 함수는 부모에서 받은 문자열의 문법이 해당 OS의 shell과 맞는지를 보장하지 않는다. Windows 실패를 이 검토에서 실행한 것은 아니다.

Zeus 적응에서는 OS·shell·실행 파일·argv·cwd·환경·인코딩·시간 상한을 실행 영수증에 묶어야 한다. POSIX 문자열을 전역 허용하는 것만으로 Windows 재현성을 얻지 못한다. 명령 예시의 `{python}` 치환도 shell 전체의 이식성을 보장하지 않는다.

### BE-03 — health 계약은 응답 본문을 요구하지만 구현은 status만 읽는다

`devops-compose.md`는 HTTP 200과 본문의 상태 필드까지 확인하라고 한다. 현재 `_http_probe()`는 URL을 열어 `r.status`만 비교한다. 응답 본문, 빌드 정체성, 의존 서비스 준비 상태를 읽지 않는다. 다른 사용자 정의 검사가 이를 보완할 가능성은 있지만 **이 probe 하나를 해당 스킬 계약의 이행으로 볼 수는 없다.**

FastAPI/scaffold 스킬은 DB 비의존 생존 경로를 권하고 DevOps 문서는 의존 DB/Cache를 health 실패 원인으로 언급한다. 두 관측은 목적이 다르므로 Zeus는 프로세스 생존, 작업 수락 준비, 실제 시나리오 성공을 서로 다른 결과로 기록해야 한다. 새 프로세스가 응답했다는 사실을 DB·에이전트·배포 준비 완료로 승격하지 않는다.

### BE-04 — 규칙 래칫은 현재 실행에서 문장 제거만 대조한다

`project-convention.md`는 규칙 수를 원장으로 래칫하라는 제안을 한다. 현재 `gate_ratchet.scan()`은 과거 stage별 `gate_check.statement`와 현행 문장 집합의 차이를 계산하고 `gate_waivers`의 키를 제외한다. `rules: N`, 정규식 내용, threshold, 대상 파일, 실행 명령은 이 함수의 대조 대상이 아니다. 같은 문장을 유지한 채 검사 기준을 낮추는 변경은 이 함수만으로 검출하지 못한다.

`test_gate_ratchet_smoke.py`도 문장 제거·추가·단계 삭제·이름별 면제·tick blocker를 대상으로 한다. 규칙의 의미를 불변으로 유지한다는 증거는 아니다. 현재 `tick.py`가 `scan()`을 소비하는 호출까지 확인했다. 완화 탐지는 검사 정의의 버전·해시·의미 변경 검토에 묶어야 하며, 규칙 수만 보존하는 방식도 동일 개수의 약한 정규식으로 바뀌는 것을 입증할 수 없다.

### BE-05 — 외부 부작용의 보장은 lease 한 개로 끝나지 않는다

`java-scheduled-batch.md`는 CAS lease를 선점한 후 외부 PG/결제를 호출하는 구간을 `at-most-once 게이트`라고 부르고 TTL을 P99+skew보다 크게 잡으라고 한다. 원문이 보여주는 설명만으로는 처리 지연의 꼬리, 프로세스 정지, lease 만료 후 이전 소유자 재개, 성공 응답 유실, 재시도 중 중복 승인을 배제하지 못한다. 그 벤더/DB 구현을 이번에 읽거나 실행하지 않았으므로 원본 시스템의 결함을 확정하는 주장이 아니다. **전역 보장으로 옮기기에는 증거가 부족하다는 채택 경계**다.

Zeus의 `ReleaseQueue`는 store transaction 안에서 owner·generation·lease와 controller lock을 대조하고 완료·heartbeat에서 다시 검증한다. 이는 현재 코드에 존재하는 제어판 경계다. 외부 배포·결제의 실행 멱등성까지 이 함수만으로 입증하지 않는다. 외부 요청 ID·수신처 멱등 처리·결과 조회·실패 복구와 별도로 실측해야 한다. 사용자의 금전 흐름 요구에서는 알려진 중복 가능성을 문서화했다는 이유만으로 수용할 수 없다.

### BE-06 — 스킬의 공통 이름 아래 특정 스택과 운영 결정을 강제한다

`devops-ci.md`는 `_common`이지만 Java/Gradle/JaCoCo 및 ArgoCD/Kubernetes 중심이다. core 자체도 Java compile/Mapper/JaCoCo를 기본으로 두면서 Python·Java·C# 스킬을 함께 선언한다. 스킬 router의 스택 마커는 파일 이름 기반으로 언어를 구분하지만 공통 DevOps 스킬은 그대로 후보가 된다. 같은 이름의 여러 파일 중 무엇이 실제 전달되는지는 trigger와 문자 예산이 정하므로, 파일의 존재나 이름 선언만으로 전체 지침이 작업자에게 갔다고 판단하지 않는다.

이번에 확인한 `config/retriever.yaml`은 8,000자 번들, 파일당 6,000자 상한과 고정 키워드 가중치다. 이는 Astra→Sol→Terra의 결과 동등성을 검증하는 자격 체계가 아니다. 상류의 동작 분할·누락 신호는 적응 후보지만, 모델 하향은 root가 설계하는 별도 검증 절차를 거쳐야 한다.

### BE-07 — 여러 스킬의 강한 문장은 서로 다른 프로젝트 선택을 섞는다

- Python 서비스는 HTTP를 몰라야 한다는 문장과 Java web 예외의 `ResponseStatusException` 권고를 섞어 domain/application에 프레임워크 의존을 넣지 않는다. Zeus의 현재 계층 계약이 우선이다.
- SQLAlchemy 문서는 migration 정본/DDL 정본 두 방식을 구별하지만 물리 스키마 스킬은 별밤의 DDL 정본과 `create_all` 금지를 보편적인 어조로 쓴다. Zeus에서 실제 선택된 SQL migration과 저장 어댑터를 근거로 결정해야 한다.
- 인증·FastAPI·scaffold의 임시 키로 기동하는 선택은 특정 앱의 개발/CI 우선순위다. 경고 로그가 있다는 이유만으로 운영 적합성을 얻지 못한다.
- `java-spring-test`는 mock과 실제 DB 통합 검사의 차이를 구분한다. 그럼에도 mock 권고를 사용자의 no-mocking 요구에 이미 합의된 것으로 넣지 않는다. 실제 서비스의 인증·계정 생성을 우회하지 않는 Python 테스트 규율은 적응할 가치가 있다.
- `canonical-schema`의 additive 버전 불변 규칙과 폐쇄 스키마는 이전 소비자의 새 필드 수용 여부까지 같이 검증해야 한다. 새 producer의 검증 PASS가 이전 reader 호환성을 의미하지 않는다.
- `logical-design`은 앱 카운트 제한의 동시성 초과를 문서화한 사례를 알려진 한계로 처리한다. Zeus의 금전적 인수 조건을 이런 역사적 판단으로 완화하지 않는다.

### BE-08 — 관측과 재현에 유용한 자산에도 실행 공백이 남는다

성공/실패 지연 분리, 오류 분모, 실제 경보 소비자·배포 브랜치·활성 프로파일 대조는 사용자가 요구한 로그·notification 체계에 유용하다. 그러나 스킬의 `측정기·문턱·소비자` 문장 자체는 notification 전달 확인과 장애 복구를 구현하지 않는다. C# POS 스킬은 테스트 코드와 설정 실적 부재를 스스로 명시한다. Java 배치 스킬도 Spring Batch 런타임 실적 부재와 스케줄러 지연 미관측을 구분한다. 이러한 정직한 한계를 유지해야 한다.

`ddl_dry_run.py`는 설정의 PG DSN에 연결하여 파일 SQL 전체를 실행한 뒤 rollback한다. 소스의 `흔적 0` 문장은 임의 SQL 전체에 대한 검증된 무해성 증명이 아니다. 실행 전 스크립트 내용·대상 DB·권한·격리·부작용 경계를 별도로 감사해야 한다. 이번에는 **읽기만 했고 실행하지 않았다.** 대상 DB에서 DDL이 받아들여지는 것과 앱·마이그레이션·복구·성능 인수가 통과하는 것도 서로 다르다.

`checks` 테스트의 `trigger_effect` 및 `db_query` 성공 사례는 `echo` 출력을 소비한다. 검사기의 출력 판정 분기 테스트로는 의미가 있지만 실제 CI 발화나 실제 DB 왕복의 영수증이 아니다. 이것을 운영 검증이라고 이식하지 않는다.

## Zeus 현재 구현과의 대조

이번 정적 대조에서 `PostgresStore`는 SQL resource를 읽고 migration/transaction 양쪽에 같은 transaction advisory lock과 lock timeout을 설정한다. `MemoryStore`는 별도 RLock/deepcopy 어댑터다. 단위 테스트에서 MemoryStore가 통과하는 것만으로 실제 PG의 드라이버·잠금·재시작·경합을 검증했다고 할 수 없다. 모든 transaction을 한 제어판 lock으로 직렬화하는 현재 방식의 포화/지연도 실측이 필요하며, 상류의 처리량·큐·풀 관측 경험을 적용할 지점이다.

`configuration.py`는 dotenv를 실행하지 않고 literal로 읽으며 ZEUS/HARNESS alias와 환경 우선순위를 처리한다. 이것은 상류의 설정 주입 경험과 연결되는 실제 구현이다. `ReleaseQueue`는 bounded retry와 generation fencing을 갖는다. `Monitoring`은 health가 120초보다 오래되면 unknown으로 투영하고 작업 완료와 배포를 분리한다. 단, 이 파일은 read-only projection이며 경보를 실제 사람에게 전달하는 소비자의 검증이 아니다. 부모 작업의 테스트 결과를 이번 읽기 기록의 실행 결과로 가져오지 않았다.

## 후속 작업 및 채택 상태

32개 경로는 정적 의미 검토 완료, subsystem 실행 검증·실제 Claude 독립 검토·Zeus 흡수는 미완료다. 필요한 순서는 다음과 같다.

1. 원본 고정 revision에서 문법 예시와 gate/parser 연결을 격리해 재현하고, 잘못된 키·다른 shell·health 본문·같은 문장 아래 검사 완화 등의 결과를 기록한다.
2. 금전 흐름과 실제 승인에 필요한 CAS·멱등·응답 유실·재시작·lease 만료 시나리오를 사람이 검토한 스펙으로 고정한다. 일반적인 mock 성공을 인수 증거로 쓰지 않는다.
3. OS별 설치·기동·정지·재시작·업그레이드·복구와 DB migration을 실제 Windows/Linux/WSL에서 검증한다. 기술 추천은 대상 버전의 공식 자료와 실행 결과로 갱신한다.
4. 로그와 오류를 local/GitHub 티켓, notification 소비, log-to-scenario 제안, 실제 테스트 영수증에 연결한다. 원문 경험의 반복 횟수나 PASS 문자열만으로 검증 강도를 높이지 않는다.
5. Astra 설계·최종 검증, Sol 중요 구현, Terra 단순 구현의 역할 전환을 동일 과업·환경·오라클·회귀 결과로 자격화한다. 이번 문자 예산 코퍼스는 그 완료 근거가 아니다.

모든 제안은 `not_approved_not_incorporated`다. 현재 분석의 목적은 코드·정책을 검토 없이 복제하는 것이 아니라, 경험과 반례를 보존하고 Zeus의 정본·권한·환경·실행 증거 체계 안에서 다시 구현할 근거를 만드는 것이다.
