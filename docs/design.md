# Codex 자기 고도화 하네스 — 목적과 초기 설계

작성일: 2026-09-07
상태: 구현 저장소의 설계 정본. 사용자 합의 사항과 구현 제안을 구분한다. 현재 구현·검증 범위는 status.md를 따른다.
재구성 기능·소유 지도(참조 전용): [context/ARCHITECTURE.md](context/ARCHITECTURE.md).

## 종합 기준안

목표는 Codex 하네스 자체를 개발하고 운영 경험과 오픈소스 연구를 통해 지속적으로 개선하는 것이다.
첫 버전의 필수 기능은 자기 개선이다. 최소 실행 기반을 부트스트랩한 뒤 같은 문제의 두 번째 발생을 훅으로 바꾸고 검증·반영하는 전체 경로를 먼저 완성한다.

### 조직과 책임

지휘자는 전체 목표·온톨로지·토폴로지와 운영/아키텍처 평가 기준을 보고 착수 및 반영을 승인한다.
리서칭 팀장은 GitHub Trending·GeekNews 등의 팀원이 제출한 근거를 검토해 개선 토픽을 올린다.
하네스 고도화 팀장은 승인된 범위를 작업으로 나누고 팀원을 생성해 PR을 받아 검수한다.
팀원은 제한된 조사 또는 구현 작업을 수행한다. 팀장은 직급이며 리서칭·고도화는 팀의 종류다.
외부 실행기는 일반 프로그램으로 기동·휴면·메시지 전달·승인 조건 확인·배포·복구를 수행한다. 네 번째 에이전트 계층으로 추가하지 않는다.

### 초기 기술 구성

- 실행 환경: Windows PC의 Docker Linux 컨테이너, Codex CLI.
- 지휘자·팀장: 독립 컨테이너. 팀원도 독립 컨테이너를 초기 제안으로 유지한다.
- 저장: PostgreSQL. 코드/설계 정본은 Git, 운영 사실의 정본은 DB 기록으로 구분한다.
- 지식: PostgreSQL + pgvector + Tree-sitter 중심의 그래프 기반 RAG를 초기 기준안으로 삼는다.
- Microsoft GraphRAG 패키지는 외부 연구 자료 종합 기능의 비교 평가 후보이며 초기 필수 의존성으로 고정하지 않는다.
- 운송: Redis 기반 메시지 버스. 구체 구현은 Streams 등 전달·복구 의미를 검토해 확정한다.
- 동시 실행: 우선 팀원 1명부터 측정한다. 고정 최대치로 확정하지 않으며 빌드·브라우저·카나리아별 자원 사용량으로 조정한다.

### 지속 운영과 작업 수명

에이전트 ID와 지식은 영속적이다. 세션은 컨텍스트 70%에서 인계를 시작하고 같은 컨테이너 안에서 교체한다.
인계 저장 완료와 새 세션의 소유권 확보를 확인한 후 기존 세션을 종료한다. 구 세션의 뒤늦은 쓰기는 차단해야 한다.
진행 중인 도구/테스트가 없는 상태에서 1시간 비활동이면 컨테이너를 종료한다.
이후 agent_id 앞으로 메시지가 도착하면 외부 실행기가 자원 여유를 확인해 기동하거나 대기열에 둔다.
진행 기록·메시지·상태는 컨테이너 밖에 남아 있어야 하고 종료/기동 경합과 중복 요청을 처리해야 한다.

### 자기 개선과 자동 반영

내부 사건과 외부 연구가 동일한 개선 백로그로 들어간다. 연구 결과가 없으면 후보 없음도 정상 결과다.
착수 승인 → 구현 → 팀장 PR 검수 → 지휘자 후보 승인 → 카나리아 → 자동 머지/점진 전환 → 효과 확인으로 진행한다.
배포 전 실패는 후보를 거부하고 운영 버전을 유지한다. 배포 후 실패는 기존 복구 경로가 이전 버전으로 되돌린다.
코드뿐 아니라 프롬프트·정책·훅·스키마·검색 방식도 개선 대상이다.
평가기는 현재 운영 버전을 기준으로 후보를 검증하며 평가 기준 개정이 같은 후보의 자기 통과 수단이 되지 않게 한다.
각 개선 시도는 유한한 예산과 종료 조건을 갖고, 조직은 새 사건·새 근거가 생길 때 후속 개선을 계속한다.

### 첫 버전의 대표 시나리오

하네스 개발 중 동일 문제의 독립된 두 번째 발생을 확인한다.
지휘자·팀장·팀원이 예방/복구 훅을 만들고 실제 증거로 검수한다.
카나리아를 통과한 변경을 자동 반영한다.
새 세션과 휴면 후 재기동에서도 그 훅과 교훈을 유지한다.
같은 문제의 재현은 예방/복구되고 정상 작업은 그대로 통과하는 것을 확인한다.
이 전체 과정의 코드·계약·사건·PR·평가·배포 관계를 그래프에서 근거와 함께 조회한다.

### 현재 구현 상태

참고 저장소 5개를 읽기 전용 조사 목적으로 복제했고 핵심 문서와 일부 구현을 확인했다.
0.1의 코어, DB/메시지 어댑터, 컨텍스트 조립, 코드 그래프, 훅 상태 전이와 CLI 스모크를 구현했다. 완성 범위와 미구현 항목은 status.md에 기록한다.
Codex 사용자 전역 권한 설정은 완료했으며 이는 하네스 내부의 승인·검증 프로토콜을 대체하지 않는다.

## 목적

자신의 코드·지침·실행 구조를 개발 대상으로 삼는 Codex 에이전트 조직을 만든다.
실행 경험과 지속적인 오픈소스 연구를 개선 가설로 바꾸고, 구현·독립 검수·카나리아·반영·효과 검증을 자율적으로 반복한다.
초기 버전부터 자기 개선이 실제로 동작해야 한다. 개선 기능을 나중에 추가하는 구조로 시작하지 않는다.

## 사용자와 합의한 요구

- 조직은 지휘자, 팀장, 팀원의 3계층이다. 리서칭 팀과 하네스 고도화 팀을 둔다.
- 에이전트 간 메시지는 who/what/why/when/where/how 육하원칙 필드를 가진 JSON으로 전달하고 스크립트로 검증한다.
- 리서처가 후보를 발굴하고 팀장이 검토한 뒤 지휘자에게 제안한다.
- 지휘자는 외부 운영·아키텍처 기준과 현재 온톨로지·토폴로지로 착수를 판단한다.
- 고도화 팀장이 팀원을 생성하고 PR을 검수한다. 지휘자의 최종 검수를 거쳐 자동 반영한다.
- 지휘자 자신의 프롬프트·승인 기준·권한 정책도 고도화 대상이다.
- Codex CLI 실행에 영향을 주는 변경은 카나리아 검증을 거쳐야 한다.
- 지휘자·팀장은 Docker로 실행하며 Redis 기반 메시지 버스를 사용한다.
- 컨텍스트 70%에서 작업 정리·온톨로지/토폴로지 갱신·상태 저장 후 새 세션으로 이어간다. 팀원도 동일한 수명주기를 따른다.
- 1시간 이상 비활동인 실행 환경은 내려가고, 메시지 호출이 오면 재기동한다.
- GraphRAG, PostgreSQL, SSOT, 주석 컨벤션, Tree-sitter를 사용한다.
- 자동화 가능한 수집·검사·상태 처리·컨텍스트 조립은 최대한 scripts로 구현한다.
- 헥사고날 아키텍처를 사용한다. 컨텍스트는 프로그램으로 구성·검증·전달하는 대상으로 다룬다.
- 같은 문제를 두 번 이상 마주하면 훅으로 코드화해야 한다.
- harness와 harness-guardian은 한 계통, baldrix는 별도 계통의 Claude 하네스이며 참고 자료로만 사용한다.
- oh-my-hermes의 학습·검증 흐름과 Q00/ouroboros의 진화·RLM 관련 개념 및 전체 설계를 도입 대상으로 연구한다.

## 구현 제안: 하나의 개선 처리 흐름, 두 가지 입력

내부 입력: 실패, 사용자 수정, 반복 재작업, 인계 손실, 자원 낭비, 구조 불일치.
외부 입력: GitHub Trending, GeekNews, 원본 저장소와 논문에서 검증한 개선 기회.

입력 → 근거 기록 → 기존 문제/지식과 연결 → 개선 가설 → 착수 계약 → 구현 PR
→ 팀장 검수 → 지휘자 후보 승인 → 카나리아 → 자동 머지/전환 → 효과 측정 → 지식 갱신.

각 착수 계약에는 해결할 문제, 기준 버전, 변경 범위, 성공 조건, 비용/시간 한도, 복구 조건을 고정한다.
후속 세대에서 명세를 개선할 수 있지만 이전 세대의 계약과 판정은 소급 변경하지 않는다.
후보는 현재 운영 정책과 평가기로 검증한다. 후보가 자기 평가 기준을 바꿔 자신을 통과시키지 않는다.
종료 상태는 성공, 회귀, 정체, 예산 소진, 취소를 구분한다. 루프가 끝났다고 성공은 아니다.

## 구현 제안: 두 번 발생한 문제의 훅 승격

1. 첫 발생부터 사건 ID, 실행 ID, 버전, 원인 후보, 도구/단계, 증거를 저장한다.
2. 동일 원인·적용 범위의 독립된 두 번째 발생을 확인하면 훅 구현을 필수 작업으로 생성한다.
3. 동일 로그 재전송·같은 사건의 중복 수집은 횟수에 포함하지 않는다. 단순 에러 문자열만으로 원인을 동일시하지 않는다.
4. 훅에는 트리거, 적용 범위, 결정론적 검사, 차단/복구/경고 동작, 시간 제한, 근거 사건 ID를 정의한다.
5. 재현 사례와 정상 반례를 검증하고 기존 PR·카나리아 경로를 거쳐 자동 활성화한다.
6. 훅의 검증과 활성화가 끝나기 전에는 해당 재발 방지 작업을 완료 처리하지 않는다.
7. 기존 훅이 같은 문제를 다루면 그 훅을 수정한다. 사건마다 별도 훅을 무한히 추가하지 않는다.
8. 해결책이 아직 없으면 감지·중단·재계획 요청 훅을 먼저 만들 수 있다. 이를 근본 해결 완료로 기록하지 않는다.

두 번째 발생은 필수 승격 트리거이고, 세 번째 발생까지 기다리는 회로 차단 규칙과는 다르다.
훅 자체의 실패·오탐·실행 비용도 관찰하고 검증된 개정 또는 대체를 수행한다.
초기 예시: PowerShell에서 codex.ps1 실행이 정책에 막히는 반복 사례는 환경에 맞는 codex.cmd 실행 어댑터/사전 검사 대상으로 삼는다.

## 구현 제안: SSOT와 지식 구조

SSOT는 사실 종류마다 정본과 쓰기 주체를 하나로 정하는 원칙이다.

| 사실 | 정본 | 파생물 |
|---|---|---|
| 코드·설정·주석·명세·훅·온톨로지 스키마 | Git의 특정 커밋 | 코드 그래프, 검색 인덱스, 생성 문서 |
| 사건·실행·승인·평가·인계·활성 버전 | PostgreSQL의 원장/트랜잭션 기록 | 현재 상태 뷰, 대시보드 |
| 관측된 컨테이너·세션·통신 상태 | 런타임 관측 이벤트 | 현재 토폴로지 뷰 |
| 외부 연구 근거 | 출처 URL/커밋과 내용 해시를 가진 보존 아티팩트 | 주장, 요약, 임베딩 |

PostgreSQL에 그래프 노드/엣지, 증거 참조, 실행 기록을 함께 관리하는 초기안을 제안한다.
대형 원문·로그는 영속 파일/아티팩트 저장소에 보관하고 DB에는 위치·해시·메타데이터를 저장할 수 있다.
Redis는 메시지 운송을 담당한다. DB 기록과 메시지 발행 사이 유실 방지를 위해 transactional outbox를 검토한다.
중복 메시지는 사건 ID/명령 ID로 멱등 처리한다. 전체 워크플로의 exactly-once를 가정하지 않는다.

온톨로지: Agent, Team, Task, Capability, Rule, Incident, Evidence, Proposal, Change, Evaluation, Release와 관계의 정의.
토폴로지: 구현/실행 중인 에이전트·컨테이너·세션·서비스·도구와 의존/통신 관계.
각 에이전트의 지식은 공통 ID/스키마 아래의 소유·접근 범위가 있는 뷰로 둔다.
선언된 설계와 관측된 실행 상태를 구분하고 차이를 drift로 기록한다.

GraphRAG는 관련 엔티티·관계·근거를 회수해 판단에 제공하는 계층이다.
LLM이 만든 추론 엣지에는 출처와 추론 상태를 붙이고 관측 사실로 자동 승격하지 않는다.
승인에 사용하는 그래프에는 소스 커밋, 스키마 버전, 인덱스 생성 버전/시점을 명시한다.
인덱스가 오래됐거나 근거가 없으면 원본 조회/재색인 후 판단한다. 인덱스는 원본에서 재구축할 수 있어야 한다.

## 구현 제안: 주석 컨벤션과 Tree-sitter

Tree-sitter로 구문 구조, 선언, import와 주석 위치를 추출한다.
정확한 심볼 해석·동적 호출·실행 토폴로지는 언어별 분석기와 런타임 관측으로 보완한다.

주석은 코드가 이미 표현하는 동작을 반복하기보다 설계 이유, 불변 조건, 근거 ID를 남긴다.
예시(아직 채택되지 않은 문법):

```python
# @invariant INV-SESSION-001
# @decision ADR-0012
# @incident INC-0042
# why: 메시지 재전송으로 동일 에이전트가 중복 기동되는 것을 방지한다.
```

주석은 정본 계약을 ID로 참조한다. 여러 곳에 계약 본문을 복사하지 않는다.
ID 유효성, 계약-코드-테스트 연결, 삭제된 심볼을 가리키는 참조를 자동 검증한다.
Tree-sitter 추출 성공만으로 주석의 의미나 구현의 계약 준수가 증명되지는 않는다.

## 구현 제안: RLM과 세션 수명

GraphRAG는 근거를 찾는 역할, RLM은 큰 자료를 외부 환경에 두고 부분 조회·계산·하위 질의·결과 합성으로 처리하는 역할이다.
70% 세션 인계는 별도의 실행 수명 정책이다. 재귀 작업 분해만으로 장문 RLM을 구현했다고 주장하지 않는다.
RLM 하위 작업에도 입력 근거, 범위, 출력 계약, 부모 작업, 비용/깊이/동시 실행 한도를 둔다.
조직 계층은 3개를 유지하고 추가 분석 작업은 팀장이 관리하는 작업 트리로 표현한다.
순차 실행도 허용하며 재귀 깊이와 컨테이너 동시 실행 수를 분리한다.
체크포인트에는 그래프 버전 외에 다음 행동, 작업 파일/커밋, 미완료 명령, 메시지 처리 위치를 포함한다.
70%는 인계를 시작하는 기준이다. 사용량을 관측하는 방법과 초과 방지는 Codex 런타임 검증 대상으로 남긴다.

## 구현 제안: 컨텍스트 프로그래밍과 헥사고날 구조

컨텍스트는 SSOT의 버전이 고정된 입력, 역할/작업 계약, 조회 결과, 편성 정책을 받아 만드는 검증 가능한 산출물이다.
스크립트가 수행할 일: 원본 수집, 변경 감지, 구조 추출, 조회, 정렬/중복 제거, 예산 배분, 필수 정보 검사, 렌더링, 저장, 인계, 훅 실행, 증거 수집.
에이전트가 판단할 일: 불명확한 요구 해석, 원인 가설, 개선 가치 판단, 설계·코드 생성, 의미적 검수.
LLM 출력도 스키마와 근거 참조를 검증한 뒤 처리 흐름으로 돌려보낸다.

처리 흐름:

사건/작업 입력 → Collect → Normalize → Retrieve → Select → Budget → Validate → Render → Dispatch
→ Observe → Persist → 다음 실행 또는 Checkpoint/Resume.

컨텍스트 구성은 세 층으로 제안한다:

- 필수: 현재 적용 정책, 역할, 작업 목표/범위/성공 조건, 활성 버전, 필요한 승인, 재개 위치.
- 선택: 관련 코드/관계, 유효한 교훈, 실패 증거, 주변 작업 상태.
- 외부 참조: 전체 로그·대형 문서·전체 그래프. 내용 해시와 조회 핸들로 접근한다.

필수 계약은 예산 때문에 잘라내지 않는다. 필수 항목이 들어가지 않으면 작업 분해나 새 세션을 요청한다.
선택 항목의 제외 이유를 기록하며 관련 정보가 없다는 결론과 조회 실패를 구분한다.
예산은 조립한 한 블록의 길이만이 아니라 역할/도구 정의·기존 대화·예상 도구 응답·출력 및 인계 여유를 포함한다.
문자 수를 토큰 수와 동일시하지 않는다. 런타임 관측값 또는 명시된 추정법을 사용한다.

ContextPacket의 초기 필드 제안:
agent_id, session_id, task_id, role, stage, policy_version, source_revision,
working_tree_fingerprint, graph_snapshot_id, checkpoint_id, required_blocks,
selected_evidence, external_refs, omitted_items_with_reasons, token_budget,
compiler_version, manifest_hash.

동일한 입력 스냅샷·선택 정책·고정된 검색 결과에 대한 최종 조립/직렬화는 재현 가능하게 한다.
온라인 검색과 LLM 요약 자체의 결정론을 가정하지 않는다. 결과 아티팩트와 모델/설정 버전을 기록한다.
캐시는 HEAD뿐 아니라 미커밋 변경, 스키마, 정책, 관련 문서 변경까지 무효화 조건에 반영한다.
정책으로 채택된 지침과 외부 문서/로그의 내용을 구분하여 외부 텍스트가 실행 정책이 되지 않게 한다.

헥사고날 구조의 의존 규칙:

- domain: 사건의 동일성/횟수, 정책, 작업·세션·훅·릴리스 상태와 불변 조건.
- application: BuildContext, DispatchTask, RecordIncident, PromoteHook, RotateSession, EvaluateCandidate 같은 유스케이스.
- ports: 코어가 필요로 하는 AgentRuntime, KnowledgeQuery, EventStore, ArtifactStore, MessageBus, ReleaseManager 등의 계약.
- adapters/inbound: CLI/scripts, 스케줄러, 메시지 소비자, 런타임 훅 이벤트 진입점.
- adapters/outbound: Codex CLI, PostgreSQL/pgvector, Redis, Docker, GitHub, Tree-sitter, 외부 자료 수집.
- bootstrap: 구체 어댑터를 생성하고 포트에 연결하는 구성 지점.
- scripts: 유스케이스를 호출하는 얇은 자동화 진입점. 도메인 규칙을 여러 셸 스크립트에 복제하지 않는다.

application은 domain 및 포트에 의존하고, 구체 어댑터는 안쪽 계약에 의존한다.
domain/application이 Redis SDK, SQL/ORM 세션, Docker 호출, Codex 프로세스 입출력 형식을 직접 알지 않게 한다.
포트 구현을 교체해 코어 규칙을 단독 테스트하고 실제 어댑터는 계약/통합 테스트와 CLI 카나리아로 검증한다.
폴더 이름만으로 아키텍처 준수를 판단하지 않는다. 정적 import 검사와 실행 경로 테스트로 확인한다.

추가 코드 조사 범위: 컨텍스트 조립·주입 및 일부 호출 연결을 정적으로 추적했다. 저장소 전체 감사나 런타임 검증은 아니다.

| 확인한 경로 | 관찰 | 우리에게 반영할 점 |
|---|---|---|
| harness `handlers/registry.py` → `prompt/seeding.py` | 세션당 한 번 원장에서 파생한 상태를 주입하며 더 큰 loadout 구조는 주석상 백로그 | 세션 초기화도 코드로 구성하고 선언과 실제 범위를 구분 |
| baldrix `cli/meeting_ingest.py` → `ground_or_drop`/`coverage_gate` → `bundle_assembler.assemble` | 근거·커버리지·영향 범위를 결정론적으로 조립 | 근거 검증과 컨텍스트 편성을 분리 |
| OMH 플러그인 등록 → `hooks/llm_hooks.py` | 첫 턴 역할 본문, 이후 활성 모드 상태를 간단히 주입 | 초기·진행·재개 시점별 편성 정책 |
| Ouroboros `runner.py` → `context_pack.py` | 파싱한 저장소 사실/검증 명령을 조립하고 HEAD와 작업 트리 파일 지문으로 캐시 관리 | 미커밋 변경까지 반영하는 사실 패킷 |
| Ouroboros `parallel_executor.py` → `context_governor.compose_context` | 프로파일 적용 경로에서 사용. 문자 예산 초과 시 기존 입력으로 폴백하며 강제 승인 게이트는 아님 | 완성된 전역 예산 강제로 오해하지 않고 필수/선택 정책을 직접 정의 |

`context_governor.py`에는 연결 전이라는 주석이 남아 있지만 현재 호출부가 존재한다.
주석과 실행 연결이 어긋나는 사례이므로 SSOT 점검은 주석 참조·호출부·테스트를 함께 추적해야 한다.

참고: [헥사고날 아키텍처 원문](https://alistair.cockburn.us/hexagonal-architecture).

## 초기 완료 기준 제안

1. 내부 실패를 기록하고 같은 문제의 두 번째 발생에서 훅을 구현·검증·활성화한다.
2. 같은 재현을 다시 실행했을 때 예방 또는 정의된 복구가 이루어지고 정상 사례는 통과한다.
3. 작은 외부 개선 후보 하나를 출처 확인부터 PR·카나리아·반영·효과 검증까지 처리한다.
4. 70% 세션 인계 및 휴면 후 재기동에도 사건 집계·개선 상태·근거가 유지된다.
5. Codex CLI를 고장 내는 후보가 카나리아에서 거부되고 운영 버전이 유지된다.
6. 활성화 이후 실패한 후보를 외부 실행기에서 이전 버전으로 복구할 수 있다.
7. 계약→구현→테스트→PR→배포→사건→훅을 그래프에서 근거와 함께 추적한다.
8. 저장된 운영 기록은 살아 있는 이전 세션 없이도 작업 재개에 충분하다.

최소 자기 개선의 수직 구현을 먼저 완성하고, 그 루프를 사용해 이후 기능을 고도화한다.
최초의 실행기·저장소·검증기·복구 경로는 부트스트랩 작업으로 구축해야 한다.

## 아직 결정하지 않은 항목

- PostgreSQL + pgvector 중심 초기안에서 사용할 임베딩 모델, 검색 결합 방식, 그래프 질의 범위와 성능 목표.

- 언어/프레임워크, PostgreSQL 버전과 확장, Redis Streams 등 구체 메시지 구현.
- 훅 컨벤션의 정확한 스키마와 런타임별 연결 방식.
- 정량 기준과 카나리아 데이터셋, DB 스키마 변화의 복구 전략.
- 실행기/복구기의 자기 변경도 기존 복구 경로가 후보를 검증하는 방식으로 구체화할 필요가 있다.
