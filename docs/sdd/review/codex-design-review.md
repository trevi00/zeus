1. Existing resources/baldrix_pipeline is advisory recommendation data, not the requested eight-stage execution state machine. Existing organization has research/improvement actors only. New spec/frontend/backend/QA-QC/devops responsibilities need explicit contracts; adding names alone does not create working teams.
2. Baldrix current source cbb5c3e6 differs from historical b9586c59. Read committed snapshots, retain new complete path inventories and scoped semantic coverage. scripts/lib/spec_bundle.py deliberately skips malformed Gherkin; validators/spec_bundle.py and spec_roundtrip.py report PASS when no spec exists. ID coverage is structural traceability, not actual executed acceptance. These defaults cannot be imported as strict readiness gates.
3. harness/scripts/engine/testgen.py emits pytest xfail(strict=False) skeletons. That is honestly labeled scaffolding but a successful pytest process can contain no successful acceptance behavior. Zeus must treat pending/skipped/xfail/missing/observed-only as non-passing for required scenarios. Do not import assertion expectations from successful logs: a recorded defect must not become the expected result.
4. Define a strict versioned JSON scenario IR with stable scenario/requirement IDs, Given/When/Then, independently authored assertion oracles, device requirements, data/reset contracts, risk/side effects and evidence references. Render human views and deterministic E2E from the same IR. Spec revisions invalidate affected approvals/runs. Exporting code is not running it.
5. Device access: local Samsung phone/tablet first; Android/One UI/WebView/build/locale/timezone/orientation and backend/data versions belong in run identity. A browser viewport or emulator cannot satisfy physical Samsung evidence. No adb/aws executable discovered yet, app/build/alpha target unknown. Never fabricate device runs or pay/reserve cloud devices as a substitute for missing configuration. Appium is execution; agent-device offers exploration/record/replay; AWS/Samsung provide device access. They are separate layers.
6. Human QA/acceptance must bind exact spec, build, device runs and expected outcomes. A CLI --reviewer human string is not authenticated human approval. Initial implementation can expose missing human authority as blocked, never claim a local click cryptographically authenticates a person. Financial scenarios need explicitly reviewed success/failure/duplicate/retry/reconciliation oracles and a real isolated test environment; no real money execution without actual scenario authorization.
7. Log actions, observations and assertions separately with trace/run/spec/scenario IDs, sequence, timestamp+observed timestamp, severity, bounded allowlisted metadata, artifact refs and dropped-event accounting. Secrets/full payment payloads are not 'log everything'. Persist actionable local notifications; outside delivery is a separate configured operation. Missing evidence produces an observable gap, not success.
8. Existing model selector correctly keeps unqualified workloads on Astra. Implementing a model name table would violate the requested progressive transfer. Qualification must bind task family, contract/guardrail/tools/model versions, independent held-out negative cases, actual provider receipts, quality and measured token/latency/cost. Changed evidence or failures revoke lower-tier eligibility. Never qualify an entire frontend team from an artifact-copy pilot.

Proposed first coherent slice: strict spec/scenario validation and eight-stage gate report, durable versioned observation/notification and trace-to-scenario proposals, deterministic human review view and real-environment verification of these native behaviors; explicit device capability probe and pinned provider integration plan. Device replay, human acceptance and live rollout stay visibly blocked until their required real target/authority exists. Keep roadmap tickets for complete provider/MCP/Storybook/team and qualification integration instead of presenting a scaffold as complete.
