## R1 · P1 · timeout이 작업을 끝내지 않고 살아 있는 I/O를 버려 둔다

`VerificationServices._bounded`는 daemon thread를 시작한 뒤 join(seconds)만 한다. 시간이 지나면 호출자에게 TimeoutError를 던지지만 worker 취소·소켓 종료·종료 확인·잔여 추적은 없다. daemon=True는 프로세스 종료를 방해하지 않을 뿐 실행 중인 스레드를 종료하지 않는다.

독립 반례는 실제 로컬 소켓으로 요청을 받고 응답을 주지 않는 상대를 만들었다. `_bounded`를 0.1초씩 세 번 호출하자 세 번 모두 timeout인데 **세 worker와 연결 대기가 계속 살아 있었다**. 마지막에 시험이 소유한 상대 소켓을 직접 shutdown한 뒤에야 스레드가 끝났다. 테스트 종료 시 전부 join하고 잔여가 없는 것을 확인했다. 실제 모델이나 운영 컨테이너는 사용하지 않았다.

이 반례는 helper의 작업 소유권을 검사한다. 실제 PostgreSQL 인증 이후 서버·네트워크가 멎는 상황에서 statement_timeout은 서버 실행에 의존하고 connect_timeout은 연결 이후 수신을 덮지 않으므로, 스레드 abandon만으로 전체 작업의 수명을 보장할 수 없다. Docker identity 조회도 같은 helper를 쓴다. 반환 기한과 작업 종료는 다른 사실이다.

### 수정 수용 기준

1. 기한 만료 시 자신이 시작한 요청/연결/자식 작업을 취소·종료하고 회수 여부를 확인한다. 취소 가능한 비동기 클라이언트, 소유한 연결 close, 격리 프로세스 등 구체 방식은 Claude가 구현한다.
2. 즉시 회수할 수 없다면 소유권을 버리지 말고 유계 회수·수량 제한·미종료 상태 및 복구 경로를 기록한다. 타임아웃을 반복해도 작업/소켓이 제한 없이 늘지 않아야 한다. 단순 daemon 변경이나 worker.join을 무한 대기로 바꾸는 것은 해결이 아니다.
3. 현재 하나의 준비 기한과 늦은 성공 거절은 유지한다. 준비 기한과 후처리 회수 기한을 분리한다면 영수증에서 각각의 의미와 잔여를 명시한다.
4. 실제 연결 후 무응답을 반복하여 반환 결과뿐 아니라 소유 worker·연결·프로세스의 종료/회수 상태를 단언한다. timeout 후 늦은 완료가 ready를 발행하지 않는 대조도 유지한다. 실제 모델 호출은 필요 없다.
