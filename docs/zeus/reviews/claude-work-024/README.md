# PR #101 3차 독립 검토: 회수 보장의 세 경계

대상 `b0e673a6e0b9dc53ddaedc1b5b0dee2883aca790`, 런타임 `02bc12313e8bdec0a826ac0fa46785907d4ee788`. 자원 등록·회수 및 단일 객체 내 한도 구현은 확인했다. 그러나 반복 실행 전체의 유계 소유와 유계 회수를 아직 보장하지 못해 병합·이슈 종료를 보류한다.

## R1 · P1 · 새 서비스 객체마다 미회수 한도가 초기화된다

unreclaimed는 VerificationServices 인스턴스에만 있다. 실제 through_harness 반복처럼 다음 스택마다 객체를 새로 만들면 이전 작업을 가진 채 한도는 0으로 돌아간다. 독립 반례에서 종료되지 않는 작업을 새 객체로 네 번 시작하자 프로세스에 4개 worker가 살아 있었고 UNRECLAIMED_LIMIT=3을 넘겼다. 같은 방식의 반복 횟수를 제한하는 장치는 없다.

worker 수명 이상으로 살아 있는 공통 소유자가 예약/등록/회수/한도를 관리해야 한다. 새 객체·동시 시작이 같은 한도를 공유하고, 완료된 작업은 회수 확인 뒤 해제한다. 실패 경로에서도 미회수 ID·개수·복구 방법을 실제 외부 영수증/로그에 남긴다. 현재 readiness 성공 반환에만 있는 unreclaimed_attempts는 timeout 실패의 보고를 대신하지 못한다.

## R2 · P1 · close/cancel 자체는 회수 기한 밖에서 실행된다

`closed = self._close_all(resources)`가 호출자 스레드에서 동기 실행된 다음에야 worker.join(RECLAIM_SECONDS)가 시작된다. 등록된 cancel/close가 멎으면 호출자도 멎고 회수 기한은 시작조차 하지 않는다.

반례는 close에서 Event를 기다리는 등록 자원을 사용했다. 준비 0.02초/회수 0.02초로 설정하고 0.3초의 여유를 줘도 호출자가 돌아오지 않았으며, 시험이 close를 풀어 준 뒤에야 종료됐다. 실제 DB가 멎었다는 실측이 아니라 닫기 동작의 정지를 주입한 동기화 반례다.

회수 기한은 cancel/close/종료 호출과 join 전체를 덮어야 한다. 정지할 수 있는 닫기 작업을 관리한다면 그 작업 자체도 R1의 소유권/한도/미완료 보고에 포함한다. 닫기용 스레드를 또 버리거나 무한 join으로 옮기지 않는다.

## R3 · P2 · 회수가 시작된 뒤 등록한 자원을 놓친다

등록은 resources.append이고 회수는 list(resources)의 단 한 번 스냅샷이다. 회수 스냅샷 직후 자원이 열리고 등록되면 close가 호출되지 않는다. 실제 코드에서도 psycopg.connect가 반환한 뒤에만 connection을 등록하므로, 연결 수립과 timeout 사이에서 이 순서가 가능하다.

독립 반례는 _close_all의 스냅샷 완료를 barrier로 삼아 그 뒤 자원을 등록했다. 회수 창이 끝나도 자원의 close는 호출되지 않았다. 기록에는 개수만 남고 후속으로 닫을 수 있는 자원 소유권은 관리되지 않는다.

등록과 취소 상태를 동기화한다. 취소된 시도에 늦게 등록하는 자원은 즉시 유계 회수 대상으로 전달하거나 추적되는 회수 큐에 넣는다. 스냅샷 전/중/후 등록을 모두 같은 계약으로 처리하고 완료까지 참조를 유지한다.
