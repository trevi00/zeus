# PR #103 독립 검토 — 포트 선택과 증거의 범위

대상 `1a161111b60d6538de3386927143d96b55cb2167`, runtime `deec4fded2a2ceb3f25d956e8cbd6d5b23840b1a`. 검토 범위와 종료 조건은 FRAME.md에 먼저 고정했다. PR #101 위 스택 변경만 판단하며 이 검토로 base를 승인하지 않는다.

## 수용하는 방향과 설계 결정

제출된 재현·소켓 표에는 WSL에서 점유한 포트를 게시했을 때 Windows와 컨테이너는 응답하고 WSL에는 LISTEN이 없으며, 점유 해제 30초 뒤에도 거절되고 컨테이너 재시작 후 LISTEN/연결이 생기는 관측이 있다. 이 재현 기제에 맞춰 게시 포트를 배포판 ephemeral 범위 밖으로 옮기는 완화 방향은 타당하다. 시간 제한 증가나 무제한 재시도는 요구하지 않는다.

**자동 컨테이너 재시작은 이번 PR에 추가하지 않는다.** 준비 실패를 기록하고 자기 일회용 스택을 정리하는 기존 흐름을 유지한다. 재시작 성공이 원래 실행 성공으로 둔갑하거나 최초 실패 증거를 덮어쓰면 안 된다. 잔여 TOCTOU를 완전히 제거할 때까지 이 작업을 보류하라는 요구도 아니다.

## R1 · P1 · 사전 점유 검사가 호출한 호스트만 본다

`published_ports.py:35–50,58–95`는 `/proc`를 읽을 수 없는 경우 Linux 기본값을 사용하고, 후보 포트는 현재 프로세스의 `127.0.0.1`에만 bind한다. Windows에서 시작하면 Windows만 검사하므로 WSL에 **이미 존재한 점유**를 배제하지 못한다. 이것은 문서가 잔여로 인정한 “검사 후 해제→게시 사이의 경합”보다 앞선 실패다.

독립 반례는 실제 Ubuntu Python 프로세스가 24000–24099 안의 포트를 먼저 bind하여 유지하게 했다. Windows의 `choose`에는 그 유효 범위 후보를 고르는 RNG만 주입했다. **WSL이 24000번을 쥔 상태에서 Windows가 [24000]을 반환했다.** 실제 소켓과 실제 WSL 프로세스를 사용했고 Docker/OS 설정은 변경하지 않았다. 검사 종료 시 자기 프로세스와 소켓을 해제했다. 결과는 counterexamples.log와 test_cross_host.py에 있다.

수용 조건:

- 배포·접속에 관련된 호스트/배포판을 명시하고, 보장하려는 포트 범위와 사전 점유를 그 환경에서 확인한다. 상대 환경을 확인하지 못하면 확인된 것으로 기록하지 않는다.
- 이 PC 지원은 Windows→Ubuntu 사전 점유와 WSL→Windows 사전 점유를 모두 고려한다. 이미 점유 중인 경우와 선택 후 발생하는 경합을 분리한다. 원격 Docker 등 미지원 topology는 명시적으로 제한하거나 완화 보장 없음으로 보고한다.
- Windows에서 가정한 Linux 기본값은 실측값과 분리하고 영수증에 범위의 출처를 남긴다. 범위 미확인·후보 고갈 fallback 이유도 구분한다. “모든 allocator 밖”은 확인된 환경에만 한정한다.
- 후보를 놓은 뒤의 경합은 남을 수 있다. 실패 진단·유계 종료·증거 보존으로 다루며 이를 위한 자동 재시작은 이번 요구가 아니다.

## R2 · P1 · 재현 도구가 고정 이름의 컨테이너를 선제 삭제한다

`wsl_port_probe.py:89–90,119–120,133–134,180–181`은 고정 이름에 `docker rm -f`부터 실행한다. “모든 실행이 고유 이름이며 다른 실행에 손대지 않는다”는 설명과 다르다. 두 번 동시 실행하면 후발 실행이 선행 실행의 컨테이너를 삭제할 수 있다. 또한 재현·소켓·잔여 측정 함수에 전체 자원 수명을 감싸는 finally가 없어 timeout/관측 예외에서 마지막 정리를 건너뛴다.

이는 직접 읽은 실행 경로에 근거한 결함이다. 기존 이름의 컨테이너를 실제로 삭제하는 위험한 재현은 수행하지 않았다.

수용 조건:

- 호출마다 UUID 등으로 고유 이름/소유 라벨을 만들고, 생성에서 확보한 ID만 정리한다. 기존 이름 삭제로 초기화하지 않는다.
- 생성·관측·타임아웃·중단·정리를 같은 소유 범위로 묶는다. 정리 결과와 정리 실패도 증거로 남긴다.
- 동시 실행의 상호 비침범, 중간 실패 시 자기 자원 정리, 정리 불가의 명시적 보고를 실제 일회용 컨테이너로 확인한다. 운영 컨테이너나 다른 실행에는 손대지 않는다.

## R3 · P2 · 재현 가능한 기제를 과거 원인 전체의 확정으로 확대했다

과거 일곱 건의 실패 시점에 해당 포트를 잡은 프로세스/소켓을 수집하지 않았다. 이번 실험은 **의도적인 bind 점유**로 같은 증상을 만들었고, 그 실험에서의 LISTEN 부재와 재시작 후 회복을 관측했다. 이것만으로 과거 점유자가 ephemeral allocator뿐이었다고 확정하거나 “일곱 건의 원인을 제거했다”고 할 수는 없다. 실제 outbound 연결/할당을 그때 관측한 것과 수동 bind는 구별한다.

30초 동안 회복을 관측하지 못했다는 사실은 “컨테이너 평생 재시도하지 않는다”와도 다르다. 문서·PR·모듈/테스트 설명에서 측정된 시간·버전·환경으로 한정한다. 과거 사례에 대한 설명은 유력 가설/동일 증상 재현으로 남겨도 이 완화의 수용을 막지 않는다.

`resume_probe.py:61–108`은 unpause/up --wait/restart 명령 **반환 뒤**, health 조회까지 마친 다음 첫 DB 요청을 보낸다. 24회 거절 0은 관측한 구간의 결과이며, 미관측 초기 구간이나 다른 CI 실행의 재개 기제를 배제하지 못한다. “가설은 틀렸다/재개 후보가 측정으로 빠졌다”를 “이번 관측에서 재현되지 않았다”로 정정한다. `gate_would_have_been_wrong`도 health보다 뒤에 첫 응답이 있었다는 시각 차이를 잘못된 게이트로 이름 붙이지 않는다.

원본 JSON은 두 호스트 각각 `cycles_where_health_was_green_before_the_first_answer=4`인데 PR 본문은 4/24로 적었다. 실제 합계는 8/24이며 이 값은 관측 순서이지 비준비 증거가 아니다. 관측 사실과 해석을 한 번에 정리하고, 기존 원본을 조용히 덮어쓰지 않는다. 이를 고치기 위해 과거 실패 재현을 무한 반복할 필요는 없다.

## 검증

- 실제 PG/Redis 일회용 스택 위에서 기존 수용 반례, 제출된 verification/port_diagnosis/published_ports 검사, 새 Windows↔WSL 반례를 함께 실행했다. **82 passed / 2 skipped / 1 failed**, 실패는 위 사전 점유 반례다. 스킵은 기본 Docker opt-in 검사 1건과 Windows의 Linux /proc 범위 읽기 1건이다. 잔여 검증 컨테이너는 0개다. 결과는 result.json 및 counterexamples.log에 보존한다.
- 전체 Ruff 통과. CI push 35045826164 / PR 35045862405 모두 attempt 1 / success, 10 checks 통과.
- environment-runs-025 두 receipt의 stdout/stderr/JUnit 해시, identity_stable, runtime→최종 head의 src/scripts/uv.lock 차이 없음 확인. 제출된 1799/1802 전체 스위트를 Codex가 다시 실행한 수치로 표현하지 않는다.
- 재현·소켓 표는 제출된 원본을 검토한 결과이며, Codex가 그 30초 Docker 충돌 실험을 새로 재실행했다고 주장하지 않는다. Codex의 독립 추가 실행은 사전 점유 선택 반례다. 모델 호출 0회.
