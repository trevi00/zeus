## Implementation review — FA-017 closure

**Verdict:** the agreed corrections are implemented as specified, the containment blast radius is right, and the new tests are honest about what they are. Three test-scope gaps and one migration-shaped regression remain.

### Failure receipt guard (`workflow.py:317-329`)
Correct and minimal. `_same_execution({**current, 'lease_owner': receipt['request']['owner']}, task)` sits inside the existing `require`, keeps the message, and leaves `request`/`identity` untouched — archived receipt ids are unaffected. The owner substitution is sound for the reason recorded in the discussion: `receipt["request"] == request` is conjoined, so `owner` compares trivially and only `id`/`agent`/`actor`/`recovery_sequence` do new work. `_same_execution`'s `type(left) is not type(right)` plus `default = 0 if key == 'recovery_sequence' else None` gives both the type rejection and the absent-key symmetry. Rejection raises inside the transaction, so rollback covers the "row byte-identical" requirement.

### Per-row containment
`claim` blocks a bad `created_at` row via `block_execution` and `continue`s (`workflow.py:106-109`); `running` blocks non-str/empty `status` and `continue`s (`execution_time.py:141-144`). Both match the existing poison-row idiom, and neither aborts the queue. `MemoryStore.scan`/`PostgresStore.scan` both materialize lists, so the `tx.put` during iteration is safe. New codes are added to `REASONS` and to the schema enum; they only produce `status='blocked'` + `authority: 'informational_only'` notices, so no new business authority is introduced.

### Concrete regressions / gaps

1. **`created_at` is now mandatory for claimability.** `require(created is not None, 'Creation time required')` permanently blocks any pre-existing row without a usable aware `created_at`. The test asserts this as intended behaviour, but nothing in the ticket docs states the migration consequence for rows written before `submit` began setting it.
2. **The `lease_owner` parameter case does not test what it claims.** With an altered owner the digest misses, so control reaches `_owned`, where the row's status is already `retry` — the `require` fails on `status == "running"` before `_same_execution` runs. `match='Stale'` matches both messages, so the two distinct mechanisms (digest miss vs. identity guard) are conflated rather than documented, and the case would pass even with the guard removed.
3. **`decisions_pending` coverage is shape-shallow.** The fixture copies a *tasks*-shaped lease into the bucket, so the row carries `agent` and no `actor`. Both sides of `_same_execution` derive from the same dict, so the "missing actor/recovery key symmetry" assertion never exercises a genuinely asymmetric row (stored `actor`, caller dict without it) — the exact over-rejection case the guard was supposed to be proved against. Likewise, `InvalidExecutionState` containment in `running`'s `decisions_pending` branch is untested.
4. **Two required cases absent:** pre-recovery receipt replayed post-recovery (would be caught by the `current["generation"] == task["generation"]` conjunct, but is unverified), and the digest pin. `expected = digest({...})` at `test_execution_identity.py:34` recomputes from the same inputs with the same function, so both sides move together if canonicalization changes; it proves the field set, not that the receipt id is unchanged from archived evidence. A literal hex constant is what case 7 asked for.

### AC4 / AC5 honesty
AC4 is genuinely advanced: real PG, real child processes, shared and nested UTF-8 cwd, foreign-lease heartbeat/fail rejection with full-`records()` equality, and sibling-row preservation across a recovery claim. The comments at `:110` and `:132` correctly label `project_context`/`retrospective` as fixture extension state and equal times as fixture inputs — no invented Zeus feature, no simultaneity claim. The evidence `scope` string names the exclusions (tenant auth, model/human E2E) rather than implying them. Given gaps 2–4, AC4 is substantially but not fully resolved.

AC5's contract text (`contracts.md:168-172`) states the UTC assumption, names OS clock-step/suspend/VM-resume as unmeasured, and refuses both the "always detects offline rollback" claim and host clock mutation. Nothing in the new tests relabels pure clock samples as those measurements. That boundary is stated as the audit required.
