# 손상된 발송 대기열 레코드 격리

기존 FA-006 / GitHub #7 / `ZEUS-fb340b746179` 개정 1의 수정입니다.
Zeus의 발송 대기열에 손상된 레코드가 있으면 전체 발송 트랜잭션이 취소되어,
앞에서 이미 전송한 메시지는 재전송되고 뒤의 정상 메시지는 계속 막혔습니다.
이제 레코드마다 독립적으로 처리하고 손상된 원문을 격리하여 정상 메시지를 계속 전송합니다.
새 이슈나 분석 후보는 추가하지 않았습니다.

## 동작과 운영 확인

```text
zeus flush
zeus inspect outbox_delivery
zeus inspect outbox_attempts
zeus inspect outbox_quarantine
```

`flush`의 JSON 응답에는 `published`, `quarantined`, `quarantined_existing`, `retry`,
`skipped`, `legacy_sent`, `error`, `examined`, `limit`가 있습니다. 이전의 단일 `published`
필드는 유지하되 반환값은 처리 결과 객체가 됩니다. 기본 호출은 최대 100개 레코드를 확인하며
영속 커서가 다음 페이지로 이동하고 마지막에 돌아옵니다. 키 순서 검사이며 FIFO를 보장하지 않습니다.
이미 처리된 기록도 페이지 용량을 사용하므로 전체 대기열 크기와 한 번의 검사 건수는 다릅니다.

스키마·전달 경로·식별자가 잘못된 레코드는 원래 위치에서 삭제하지 않습니다. 별도의 해시 결속
격리 사본과 고정된 원인 코드가 남습니다. 같은 손상 레코드를 다시 만나도 격리 사본과 이벤트를
중복 생성하지 않습니다. 전송 전 오류가 수정되면 다음 검사에서 다시 확인합니다.

전송 의도와 메시지 내용 해시는 Redis 호출 전에 PostgreSQL에 먼저 기록합니다. 한 번이라도
전송 의도를 기록한 메시지의 내용을 바꾸려면 새 메시지 식별자가 필요합니다. 전송 직전에 현재
의도와 원문을 다시 확인하므로 다른 실행이 대체한 의도는 전송하지 않습니다.

전송 성공 시 Redis 엔트리 ID, 시각, 시도 번호를 보존합니다. 전송 장애는 재시도 대상으로 남기고
다음 정상 레코드를 계속 처리합니다. 예기치 않은 프로그램 오류는 기록한 뒤 호출자에게 다시
전달하고, DB 오류도 숨기지 않습니다. 이전 정상 레코드의 완료 기록은 함께 되돌리지 않습니다.

Redis 전송 뒤 응답이나 DB 커밋이 유실되면 동일 메시지가 다시 전송될 수 있습니다.
수신자는 변경되지 않은 메시지 식별자로 중복을 제거해야 합니다. 전송 영수증은 버스 등록 응답이며,
수신자의 업무 완료·제품 인수·사람 승인이 아닙니다. 새 영수증 없이 기존 `sent: true`만 있는
레코드는 `legacy_sent`로 구분합니다.

모니터의 전체 현황에는 전송 응답·격리·재시도·미완료 의도·오류의 건수가 표시됩니다.
격리나 미완료 상태가 남으면 이후 정상 검사 뒤에도 상단 경고가 유지됩니다.
원문과 임의의 예외 문장은 모니터에 표시하지 않습니다. 전체 기록 조회 권한과 승인 권한은 별개입니다.

## 검토와 실제 검증

- `baseline.json`: 수정 전 실제 PostgreSQL·Redis에서 첫 메시지 두 번 전송, 완료 기록 취소,
  뒤의 정상 메시지 미전송을 재현했습니다. 기준 커밋과 원시 관측을 포함합니다.
- `claude-design.md`, `root-design.md`, `claude-implementation.md`, `claude-final.md`:
  실제 Claude CLI의 독립 검수, 루트의 합의·이견 판단, 최종 승인입니다.
- `target-tests.log`: 메모리와 실제 격리 PostgreSQL·Redis를 사용한 58개 검사 통과.
  코드 오류 전파, 동시 실행, 식별자 재사용, 전송 직후 DB 실패, 제한된 페이지 검사,
  원문 보존 및 모니터 경고 지속을 포함합니다.
- `windows-full-tests.log`: 최종 구현의 Windows 전체 회귀 테스트 **736 passed, 152 skipped**.
  일반 실행에서 제외되는 통합 항목은 위의 실제 서비스 검사와 구분합니다. Ruff도 통과했습니다.
- `live-verification.json`: 기존 재현 환경을 그대로 사용한 실제 `zeus flush`, 손상 레코드 격리,
  실제 Redis ACK를 버리는 장애 주입, 실제 XADD 직후 PG 커밋 실패 주입과 재시도 복구.
  네 개 메시지의 전송 응답과 한 개 격리 기록을 확인했습니다.
- `browser-verification.json`, `monitor-snapshot.json`, `desktop.png`, `phone-width.png`:
  실제 로컬 HTTP 모니터와 Chrome에서 경고·건수·원문 비노출·가로 넘침·브라우저 오류를 검사했습니다.
  휴대폰 너비 재현이며 삼성 실기기 검증은 아닙니다. 격리 검사에서 Docker 자료를 수집하지 않아
  해당 수집 불가 경고가 함께 보이며, 이를 정상으로 위장하지 않았습니다.

첫 통합 검사 호출은 전용 Redis 포트 환경변수를 빠뜨려 기본 포트 연결 오류가 발생했습니다.
같은 코드에 전용 포트를 명시한 최종 호출은 58개 모두 통과했습니다. 원본 운영 Redis나
기존 Docker 배포는 변경하지 않았습니다. 별도의 시험 컨테이너·네임스페이스·PG 스키마를 사용했습니다.

한 번의 PostgreSQL 전송 트랜잭션은 여전히 부트스트랩 전역 잠금을 사용하므로 단일 전송 지연 동안
다른 원장 쓰기가 대기할 수 있습니다. 격리·시도 이력은 보존되며 자동 삭제하지 않습니다.
모니터의 상태 집계는 현재 전체 전송 상태 기록을 읽습니다. 대규모 운영용 보존·집계 정책과
외부 웹훅 전달, 실제 사용자 인수, 전체 하네스 운영 전환은 이번 검증으로 완료됐다고 주장하지 않습니다.
