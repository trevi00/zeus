## What the code actually does today

`_related_checked` (`execution_recovery.py:64`) hard-rejects every phase except `threshold_review` — "No recovery coupling handler for this decision phase". The threshold handler is the template worth copying: it (a) re-derives the decision identity from the request (`digest([request['id'], row['actor']])`), (b) requires the request to be in the *actor-specific* awaiting state or failed with `failed_decision == row['id']`, (c) re-checks `digest(record) == request['binding']`, and (d) returns a dict hashed into `related_hash`, re-checked at `apply` (`:184`) and on replay (`:158`, `:173`).

The generic machinery already gives you what's needed for the other phases: `expected_hash` on the row itself, `ticket_binding(tx, details)` at `:187`, evidence artifact re-read via `_evidence`, and the 15-minute window. So per-phase work is *only* `_related_checked` plus, for one phase, the un-restore of a native failure state.

## Per-phase authoritative related state

**diagnose** — created in `executor.py:446` keyed `digest({"task": task_id, "attempt": attempt})`, input carries `source_task_id`, `occurrence_id`, `evidence_ref`, `known_causes`. The trap you flagged is real: the source task is *failed* and may already have been resumed by another recovery, so `digest(source_task)` is the wrong binding — it changes on every subsequent attempt/generation bump and would falsely invalidate a still-valid diagnosis. Bind instead to what the diagnosis is actually about: `row['id'] == digest({'task': input['source_task_id'], 'attempt': attempt_of_that_occurrence})`, source task exists and its `attempt` at the time is immutable in the key, `artifacts.text(input['evidence_ref'])` still resolves, and **`tx.get('incidents', input['occurrence_id']) is None`** — a recorded incident means `_commit_decision:580` already fired; resuming would re-run `record_incident`, which at `service.py:51` requires byte-identical content and would hard-fail after the attempt is spent. Do *not* pin `known_causes` to the current `tx.scan('incidents')`: it legitimately grows, and the diagnosis prompt explicitly tolerates that.

**research_lead** — `workflow.py:305` writes status `deferred_pending_source_audit`, not `pending`; `decide_one:467` never leases it. Recovery must not resurrect it into `retry` — that would manufacture a reset right the workflow deliberately withholds. Related state: `tx.get('research_topics', row['discovery_id'])` with `decision_id == row['id']` and `research_discoveries[discovery_id]['status']`; reject unless the discovery has been promoted out of `deferred_pending_source_audit` by native policy. Practically: return the binding, and let `_eligible` continue to gate on `blocked/failed/expired`.

**proposal / review_lead / review_conductor** — the originating report is `row['message']`, and `workflow.py:270` already stored `workflow_inbox[message_id]` with a hash. So bind `digest(row['message']) == inbox['hash']` for `tx.get('workflow_inbox', row['id'])` — cheap, exact, and catches a mutated report. Beyond that:
- `proposal`: nothing else; `require_dispatch`/`ticket_binding` re-run at commit.
- `review_lead`: `releases.propose` (`releases.py:53`) is content-addressed on `{candidate, policy}` and idempotent (`:58`), so a partially-committed lead review is safe to re-run *unless* a review already landed. Pin `release = tx.get('releases', digest({...}))`; if present, require `status in {'candidate','reviewed'}` and no review by `row['actor']` — otherwise `Releases.review:84` ("Duplicate release review") kills the retry. Also pin the hook when `candidate['hook_id']`: `digest(hook['spec'])` and `hook['status']`, since `_review_hook:667` passes `digest(hook["spec"])`.
- `review_conductor`: `release = tx.get('releases', input['release_id'])`; require it exists, `candidate['revision'] == input['candidate']['revision']` (mirrors `releases.py:73`), `status in {'candidate','reviewed'}`, no prior review by the actor, and `tx.get('release_queue', release_id) is None`. Additionally pin `improvement_loops[message['correlation_id']]` — `_commit_decision:624` mutates `reworks`/`rejected_trees`; a loop that reached `stagnated`/`budget_exhausted` since failure must reject, and the tree/rework count belongs in the hash.

**audit_review** — strongest constraint, and it must be recomputed, not snapshotted. `research.review:301` requires `review.binding == data['binding'] == binding(tx, audit_id, proposal)`. So `_related_checked` should call `audit_gate.binding(tx, input['audit_id'], input['proposal'])` and require equality with `input['binding']`, plus `row['id'] == digest({'binding': input['binding'], 'actor': row['actor']})` (`research.py:283`). Reject if a review by this actor already exists (`any(r['review']['binding']==binding and r['review']['actor']==row['actor'] for r in tx.scan('research_reviews'))`) or if `tx.get('research_approvals', binding)` exists — the outcome landed. Note `binding()` itself requires an active release (`audit_gate.py:19`), so a rollback correctly makes recovery fail rather than burn budget.

## The claim-vs-commit gap

Currently the related hash is verified only inside `apply`. Nothing re-verifies at lease acquisition in `decide_one` (`executor.py:466`) or at `_commit_decision`, so between recovery and the model run a release can get reviewed, a loop can stagnate, or the audit binding can shift — the attempt is spent and the commit dies. Bounded fix, no new policy: persist `recovery_binding = digest(related)` on the row alongside `recovery_receipt` (`:194`), then re-derive and compare in exactly two places — in `decide_one` before the `status="running"` update (mark `superseded` with the reason on mismatch, mirroring the existing `TicketSuperseded` branch at `:474`), and in `_commit_decision` right after `_owned` (`:571`), next to the existing `ticket_binding` try/except. Both call the same `_related_checked`, so there is one authority. Clear the field once the decision succeeds.

Two cautions: `_related` catches only `OSError/ValueError/KeyError/TypeError`, so per-phase handlers must not raise other types; and `digest(related)` must stay order-stable — `tx.scan` results need explicit sorting (as `audit_gate.py:11` does) or the hash will flap.
