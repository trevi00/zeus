Prior findings do hold up: the strict `_same_execution` tuple, per-row `contain_with_notice`, budget-carrying `request_budget()`, and the global `pg_advisory_xact_lock(734219)` in `PostgresStore.transaction` (store.py:88) close the cross-process TOCTOU between `contain_time` and `running()`. Remaining concrete blockers:

**1. `pin_clock` marries a caller-supplied wall to a self-sampled monotonic (execution_time.py:84-97).** `now` comes from the caller; `mono = time.monotonic()` is taken inside. Nothing requires the two to be contemporaneous, and `Workflow.claim(now=...)` (workflow.py:81, reaching `pin_clock` at :158) is a public injection point. A pin written with an injected `now` makes every later real-clock validation compute `delta_wall - elapsed ≈ offset`; past `CLOCK_TOLERANCE_SECONDS` that is a durable `ClockDiscontinuity` → blocked row → operator repair packet. tests/test_workflow.py:23 already injects +2 s; it passes only because 2 < 5. Same structure in executor.py:533→541. Fix: derive wall and monotonic from one sample inside `pin_clock`, or reject a `now` that is not within tolerance of the host reading.

**2. Event identity defeats both the conflict check and retention (execution_time.py:113-122).** `observation` carries `wall` (µs) and `monotonic` (float), so `digest(event)` is unique per occurrence: the `require(... 'Conflicting execution time event')` branch is unreachable for observation-bearing reasons, and the same execution can produce two rows because the `observation=None` paths (workflow.py:151, executor.py:535) digest differently from the `active()`-raised `deadline_exceeded`. `execution_notices` is keyed semantically (execution_notices.py:21-29), so the two buckets legitimately diverge and the `len(events) == len(notices) == 1` assertions (test_execution_time.py:51, 118) are load-bearing on containment firing exactly once. No retention exists for the bucket — `maintenance.collect` covers artifacts only, POLICY has just `artifact_retention_days`/`stream_retention_entries` — and `cli inspect execution_time_events` scans it unbounded.

**3. `decisions_pending` has no deadline producer.** `deadline()` falls back to `message.when.deadline` only for `tasks`; no writer sets `execution_deadline` on a decision except `ExecutionRecovery.apply` (execution_recovery.py:222). So `deadline_remaining` is `None`, `remaining_seconds` returns the full `POLICY.decision_seconds` every tick, and decision executions are bounded only by the 1200 s lease — the durable deadline half of this module is vacuous for that bucket.

**Minor:** `pin_clock` computes `remaining = due - now` against the earlier wall sample while elapsed accrues from the later monotonic origin, overstating budget by that gap; and the value returned by `remaining_seconds` does not subtract its own commit/return time before `run()` re-anchors it at app_server.py:141.
