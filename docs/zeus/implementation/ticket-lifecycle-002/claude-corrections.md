## Remaining items

**1. The lease no longer covers the critical section (should fix).** Verification is now inside the claim, but the lease is only renewed at `:157`, after `verify_closed` *and* the issue read/list. `verify_closed` calls `policy()` twice (once at `:176`, once inside `authority.verify` at `:70` — six git subprocesses) and runs one `ssh-keygen` per signature at `timeout=30`, with up to 20 signatures permitted (`ticket_authority.py:74`). Worst case that segment alone exceeds the 300s lease before renewal, and adding the `_read`/`issue list` calls at 60s each makes it worse. The failure is safe — `_owned` raises "Stale ticket sync" and marks `needs_attention` — but it makes closed-ticket sync unachievable for a multi-signer policy with any slow subprocess. Renew the lease immediately after the authority block at `:98`, before the first remote call.

**2. Reasserting OPEN supersedes in-flight local work (should fix or document + test).** `reopen(..., expected_status="open")` exists to re-authorize a remote state projection, but it goes through `transition`, which increments `lifecycle_sequence`. That supersedes every dispatch (`:48-50`) and, more importantly, makes `ticket_binding` raise `TicketSuperseded` for any active task, since bindings compare `lifecycle_sequence` directly. So fixing a purely remote divergence discards local execution work even though the ticket content and acceptance state are unchanged. Skipping the dispatch loop is not sufficient — the sequence itself is the invalidator. Either keep it and document it explicitly (conservative direction, defensible) with a test asserting the supersede is intentional, or separate state-projection authority from the lifecycle sequence. `test_consumed_reopen_does_not_override_later_manual_close` has no active dispatch, so nothing currently pins the behavior either way.

**3. The reopen projection path validates only the last node (one line).** Your claim about full-chain traversal is accurate for `transition` and for closed projection. The gap is the other branch: `github_tickets.py:91-98` calls `event_document` alone, so a tampered older event does not block a reopen-authorized state projection. Add `verify_chain(tx, ticket)` there for symmetry — low severity since reopen only opens an issue, but it is the one asymmetry left.

**4. `reopen` lacks the replay marker `close` now has.** `close` returns `{decision, replayed, verification}`, but `reopen` returns a bare event on both the fresh path (`:163`) and the replay path (`:157`), so a caller cannot distinguish them — the same ambiguity you just fixed for close. Lower risk because reopen removes authority, but the CLI emits both shapes and the inconsistency will be confusing.

**5. No symmetric escape for an external reopen of a closed ticket.** `test_consumed_close_does_not_override_external_reopen` correctly refuses to silently re-close, but the only remedy is a full local reopen plus a freshly signed close — which records a "reopened" event for a recurrence that never occurred. That is arguably the right conservatism (don't fight a human who reopened the issue), but it should be stated in the design so the resulting lifecycle history isn't read as a real recurrence.

**Nits:** `_evidence` reads each evidence artifact twice — `text(ref, 1MiB)` then `document(ref)` unbounded (`:81`, `:84`); the hash check makes it safe, but passing the bound through `document` would halve the I/O on the 8 MiB path. `verify_closed` re-runs full signature verification on every sync of a closed ticket; caching on `(event_id, policy_commit)` would avoid repeated subprocess work now that it holds the lease.
