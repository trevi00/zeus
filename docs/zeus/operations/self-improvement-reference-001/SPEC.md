## Fixed acceptance matrix for the design

| Boundary | Required decision/evidence |
|---|---|
| Normal | Exact failure -> scoped investigation -> named correction -> independently verified result |
| Minor deviation | Record and continue with explicit authority; do not invent successful execution |
| Material failure | Reachable acceptance breach and evidence; block only affected scope |
| Recurrence | Distinct attempts, not replayed events; two strikes trigger source-backed investigation |
| Ownership/restart | One successor claim, fencing, no retry from unknown execution; preserve lineage |
| Timeout/cancel | Bounded work and cleanup; no silent budget or deadline increase |
| Missing evidence | Unknown remains unknown; model prose never becomes verified knowledge |
| Promotion | Verified acceptance separate from cache, research and operating delivery |
| Platform | Windows/WSL/Linux paths, process ownership and storage assumptions made explicit |
| Observation | General/development/operations events with correlation and safe reason codes |
| Team | Reuse roles/transport; add responsibility only with a concrete owner and handoff |
| Ouroboros whole scope | All tracked paths accounted for; capability-to-Zeus SSOT mapping and justified disposition; no unreviewed path at whole-analysis closure |
| Absorption | Implemented and independently verified capability tracked separately from analysis; overlap enhances an existing owner instead of creating duplicate authorities |
| Out of scope | Upstream installers, fresh daemon, broad UI redesign, automatic production merge/deploy |
